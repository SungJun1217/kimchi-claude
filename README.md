## 무엇을 고치나

클로드 코드가 한국어로 답할 때 나오는 세 가지 어색함을 다룹니다.

<!-- kimchi-ignore-start -->
| 유형 | 예 | 이렇게 씁니다 |
|---|---|---|
| 🔤 직역 신조어 | `thin contract` → "얇은 계약" | 결합도를 낮춘다 |
| 🏢 판교어와 한영 혼용 | "이 컴포넌트의 state를 업데이트하고 디플로이하시죠" | 상태를 갱신하고 배포합시다 |
| 📐 번역체 문장 구조 | "우리는 캐시를 재생성한다", "당신의 코드" | 캐시를 다시 만듭니다, 이 코드 |
<!-- kimchi-ignore-end -->

세 유형이 서로 반대 방향으로 당깁니다. 첫째는 영어를 너무 많이 옮겨서, 둘째는 너무 적게 옮겨서
생깁니다. 그래서 "영어를 줄여라" 나 "영어를 써라" 중 어느 쪽도 답이 아니고, **용어별로 정착된
표기를 고정**해야 합니다.

> [!NOTE]
> **고치지 않는 것:** 코드, 식별자, 명령어, 파일 경로, 제품과 라이브러리 이름, 로그와 오류 메시지
> 원문, 소스 파일 내용, 코드 주석. 영어로 물으면 영어로 답하고 규칙이 개입하지 않습니다.

## 어떻게 동작하나

이 플러그인은 두 층으로 되어 있고, 두 층이 **정반대 원칙**으로 동작합니다.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="assets/layers-dark.svg">
  <img src="assets/layers-light.svg" width="100%" alt="플러그인의 두 층. 왼쪽은 항상 켜진 말투 층으로 규칙표가 출력 스타일로 생성되어 시스템 프롬프트에 들어가고 훅이 산출물을 검사한다. 오른쪽은 필요할 때 여는 한국 개발 지식 스킬 다섯 개다">
</picture>

말투는 매 문장에 적용되어야 하니 모델의 판단에 맡길 수 없습니다. 그래서 스킬이 아니라
시스템 프롬프트입니다. 반대로 인코딩 지식은 인코딩을 건드릴 때만 필요합니다. 그래서
스킬입니다. 항상 켜져 있는 비용은 스킬 설명 네 줄, 약 330토큰입니다.

이 구분을 흐리면 출력 스타일의 6000자 상한이 즉시 터집니다.

아래 숫자는 `npm run build` 가 써 넣습니다. 손으로 고치지 마십시오.

<!-- kimchi:counts -->
| 갈래 | 개수 | 누가 막나 |
|---|---|---|
| 치환 | 421 | 린터가 자동으로 고친다 |
| 정규식 | 70 | 린터가 잡아서 알려 준다 |
| 프롬프트 | 102 | 문자열로 못 잡는다. 출력 스타일만이 막는다 |
| **합계** | **593** | 그중 49개가 출력 스타일 본문에 들어간다 |
<!-- /kimchi:counts -->

<details>
<summary><b>출력 스타일 본문에 무엇이 들어가나</b></summary>

<br>

출력 스타일 본문은 분량 상한이 있어 규칙 전부를 담지 못합니다. 순위가 `핵심`인 것부터
담고, 문장 구조처럼 예방밖에 방법이 없는 규칙과 용어처럼 린터도 잡을 수 있는 규칙에 각각
예산을 배정합니다. **린터는 커밋 메시지와 문서 파일만 보고 대화는 보지 못하므로**, 용어
규칙도 본문에 있어야 대화에서 효과가 납니다.

같은 순위 안에서는 짧은 규칙이 먼저 들어갑니다. 상한이 빡빡할 때 긴 `핵심` 규칙이 떨어지고
짧은 `보통` 규칙이 대신 들어갈 수 있습니다. 남은 자리를 버리지 않는 쪽을 택한 결과입니다.

본문에 담기지 못한 규칙은 린터가 잡거나(치환·정규식), `natural-korean-writing` 스킬이
요청 시 펼쳐 봅니다. "이 문서 말투 좀 다듬어줘" 처럼 글을 검토해 달라고 하면 전체 표를
엽니다. 어떤 규칙을 항상 켜진 본문에 꼭 넣고 싶으면 `순위`를 `핵심`으로 올리면 됩니다.

</details>

<details>
<summary><b>왜 스킬이나 슬래시 커맨드가 아니라 출력 스타일인가</b></summary>

<br>

플러그인이 번들한 출력 스타일에 `force-for-plugin: true`를 달면 사용자가 고르지 않아도
적용되고, 스타일 본문은 대화 컨텍스트가 아니라 **시스템 프롬프트**에 들어갑니다. 매 요청마다
다시 전송되므로 대화가 길어져 컨텍스트가 압축되어도 사라지지 않습니다.

스킬이나 슬래시 커맨드는 사람이나 모델이 무언가를 불러와야 동작합니다. 말투는 매 문장에
적용되어야 하는 규칙이라 그 판단에 맡길 수 없습니다.

</details>

## 산출물을 지키는 훅

대화는 출력 스타일이 맡고, **저장소에 남는 글**은 훅이 한 번 더 봅니다. 하나의 프로세스가
세 가지를 판정하고, 둘이 동시에 걸리면 차단이 이깁니다.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="assets/guard-dark.svg">
  <img src="assets/guard-light.svg" width="100%" alt="플러그인 훅이 세 가지로 개입하는 모습. 영어 저장소에서는 커밋을 영어로 쓰라고 안내하고, 주민등록번호가 든 파일 쓰기는 막고, 어색한 커밋 메시지는 고칠 표현을 알려 준다">
</picture>

<sub>그림 속 메시지는 훅에 합성 입력을 넣어 받은 실제 출력입니다.</sub>

| | 대상 | 기본 동작 |
|---|---|---|
| 🔴 **개인정보** | 셸 명령과 사람이 쓰는 파일 (이미지·잠금 파일 같은 생성물은 뺍니다) | 주민등록번호로 보이는 값이 있으면 **막습니다.** 전각 숫자로 적어도 잡습니다 |
| 🟠 **말투** | 커밋 메시지, 한국어 문서 파일 | 고칠 표현과 이유를 **알려만 줍니다** |
| 🔵 **저장소 언어** | 세션 시작 | 이력이 분명히 영어일 때만 커밋과 PR을 영어로 쓰라고 안내합니다 |

> [!IMPORTANT]
> 훅이 실패하면 아무것도 출력하지 않고 조용히 비켜납니다. 훅이 깨져서 작업이 막히는 것은
> 검사 하나를 놓치는 것보다 나쁜 실패입니다. 모든 도구 호출마다 돌기 때문에 한 번에 약 80ms
> 안에 끝나도록 유지합니다.

### 저장소의 산출물 언어

오픈소스에 기여할 때는 대화는 한국어로 하면서 커밋 메시지는 영어로 써야 합니다.
이 플러그인은 그것을 **설정 없이 추론합니다.**

설정 파일을 만들라고 하지 않습니다. 아무도 만들지 않을 것이고, 저장소가 이미 답을
갖고 있습니다. 커밋 이력과 README 를 보면 이 팀이 어느 언어로 쓰는지 알 수 있습니다.

| 판정 | 근거 | 동작 |
|---|---|---|
| 🇺🇸 영어 | 최근 커밋 제목 40개 중 한글이 10% 이하 | 커밋과 PR 은 영어로 쓰라고 알려 줍니다 |
| 🇰🇷 한국어 | 60% 이상 | 아무것도 알려 주지 않습니다. 출력 스타일이 이미 그렇게 시킵니다 |
| 🤷 혼용·알 수 없음 | 그 사이, 또는 표본이 3개 미만 | **개입하지 않습니다** |

양쪽 문턱을 다 보수적으로 잡았습니다. 오류의 값이 비대칭이기 때문입니다 — 아무 말도 하지
않는 실수는 값이 싸지만, 영어로 쓰라고 잘못 지시하는 실수는 팀 관행을 거스르게 만듭니다.

문서는 글자 비율로 봅니다. 긴 영어 README 에 한국어 한 줄이 섞인 것은 영어 문서이고,
절반씩 섞여 있으면 개입하지 않습니다. 코드 블록은 판정에서 뺍니다.

사용자가 한국어로 쓰라고 하면 추론보다 그 말을 따릅니다.

## 한국 개발 현실 지식

클로드가 한국 서비스를 만들 때 매번 틀리는 것들을 미리 알고 있게 합니다. **설명의 절반은
직접 구현하지 말라고 말리는 일입니다.**

| 스킬 | 가장 값어치 있는 내용 |
|---|---|
| 🪪 `korean-identifiers` | 주민등록번호는 2020년 10월부터 뒷자리가 임의 발급이라 **체크섬 검증이 통하지 않습니다.** 검증하는 코드는 정상 번호를 거부합니다 |
| 📅 `korean-datetime` | 음력 공휴일을 직접 계산하면 반드시 틀립니다. 공공데이터포털에서 받습니다. 대체공휴일 규칙은 설·추석만 토요일을 뺍니다 |
| 🔠 `korean-encoding` | macOS 에서 올린 파일 이름은 NFD 라서 서버의 NFC 와 다릅니다. 눈으로는 구별할 수 없습니다 |
| 📞 `korean-formats` | 전화번호를 고정 자리수로 검증하면 서울 번호(02)와 대표번호(1588)를 거부합니다 |
| ✍️ `natural-korean-writing` | 규칙표 전체. "이 문서 말투 좀 다듬어줘" 처럼 글을 검토해 달라고 할 때 펼칩니다 |

각 스킬에는 **동작하는 코드**가 들어 있습니다. 산문으로만 설명하면 클로드가 다시 짜면서
또 틀립니다. `skills/*/examples/*.mjs` 는 `npm test` 가 검증합니다.

## 설치

클로드 코드에서 마켓플레이스를 추가하고 플러그인을 설치합니다.

```text
/plugin marketplace add SungJun1217/kimchi-claude
/plugin install kimchi-claude@kimchi-claude-marketplace
```

활성화하면 바로 적용됩니다. 따로 고를 것이 없습니다.

## 설정

모두 환경변수입니다. 기본값은 가장 조용한 쪽입니다.

| 환경변수 | 기본값 | 동작 |
|---|---|---|
| `KIMCHI_DISABLE=1` | 꺼짐 | 훅을 완전히 끕니다 |
| `KIMCHI_AUTOFIX=1` | 꺼짐 | 커밋 메시지와 문서의 표기 오류를 자동으로 고칩니다 |
| `KIMCHI_BLOCK=1` | 꺼짐 | 말투 위반이 있으면 커밋과 문서 쓰기를 막습니다 |
| `KIMCHI_PII=warn` | 차단 | 주민등록번호를 찾아도 막지 않고 알려만 줍니다 |
| `KIMCHI_PII=off` | 차단 | 주민등록번호 검사를 끕니다 |
| `KIMCHI_REPO_LANG=off` | 켜짐 | 저장소 산출물 언어 추론을 끕니다 |

`KIMCHI_BLOCK`은 기본으로 끕니다. 문체 때문에 작업 흐름을 끊으면 재시도 턴을 낭비하고, 최악의
경우 클로드가 원래 하려던 일을 잊습니다. 문체가 작업을 방해하면 그것이 더 큰 실패입니다.

## 규칙 추가하기

`rules/` 안의 마크다운 표에 한 줄을 더하고 다시 생성하면 됩니다.

```markdown
| 원어 | 쓰지 말 것 | 쓸 것 | 이유 | 검사 | 순위 |
|---|---|---|---|---|---|
| thin contract | 얇은 계약 | 낮은 결합도 | 은유를 직역해 뜻이 사라졌다 | 치환 | 핵심 |
```

```bash
npm run build   # output-styles/natural-korean.md 를 다시 만든다
npm test        # 생성물이 최신인지 확인하고 시험을 돈다
```

`검사` 칸의 세 값이 세 가지 실제 능력에 대응합니다.

| 값 | 뜻 |
|---|---|
| `치환` | 문자열로 잡히고, 쓸 것으로 그대로 바꿔도 뜻이 상하지 않는다. 자동 교정 대상 |
| `정규식` | 잡을 수는 있지만 문맥을 봐야 고칠 수 있다. 경고만 한다 |
| `프롬프트` | 문자열로 잡을 수 없다. 출력 스타일만이 막을 수 있다 |

`순위`(`핵심`/`보통`/`참고`)는 출력 스타일에 담을 분량을 자르는 기준입니다. 자료가 수백 개로
자라도 스타일 본문은 상한까지만 담습니다.

<details>
<summary><b>영어 낱말 뒤 조사 — 철자가 아니라 발음으로</b></summary>

<br>

한국어 조사는 앞말의 **발음**이 결정합니다. 철자가 아닙니다. 그래서 `commit을`은 맞고
`commit를`은 틀립니다. 커밋의 끝소리에 ㅅ 받침이 있기 때문입니다.

이 판정은 규칙표가 아니라 `hooks/lib/particle.mjs` 가 합니다. 낱말마다 한 줄씩 넣는
방식으로는 영어 낱말을 덮을 수 없습니다.

<!-- kimchi-ignore-start -->
| 입력 | 고친 결과 | 이유 |
|---|---|---|
| `commit를` | `commit을` | 커밋 — ㅅ 받침 |
| `cache을` | `cache를` | 캐시 — 받침 없음 |
| `3을` | `3을` | 삼 — ㅁ 받침 |
| `S3을` | `S3를` | 에스쓰리 — 글자가 붙으면 숫자를 영어로 읽습니다 |
| `SQL를` | `SQL을` | 에스큐엘 — 두음자어는 글자로 읽습니다 |
| `JSON로` | `JSON으로` | 제이슨 — 낱말로 읽는 두음자어입니다 |
| `kubernetes를` | 손대지 않음 | 읽는 법을 모릅니다 |
<!-- kimchi-ignore-end -->

마지막 줄이 설계 원칙입니다. **모르면 판정하지 않습니다.** 틀린 자동 교정은 없는 것보다
나쁩니다.

</details>

<details>
<summary><b>자동 교정의 조사 함정</b></summary>

<br>

<!-- kimchi-ignore-start -->
치환할 때 한국어 특유의 함정이 있습니다. "얇은 계약**을** 유지"에서 "얇은 계약"을
"낮은 결합도"로 바꾸면 "낮은 결합도**을** 유지"가 됩니다. 받침이 사라졌기 때문입니다.
<!-- kimchi-ignore-end -->

그래서 자동 교정은 바꾸기 전에 **마지막 음절의 받침 유무가 같은지** 확인하고, 다르면서 뒤에
조사가 붙어 있으면 건너뜁니다. 대신 경고로 알립니다.

</details>

<details>
<summary><b>검사에서 빼기 — 나쁜 예를 일부러 인용할 때</b></summary>

<br>

문체 가이드나 규칙 문서는 나쁜 예를 일부러 인용합니다. 그것까지 지적하면 쓸 수 없으니 표시로 뺍니다.

```markdown
<!-- kimchi-ignore-file -->          문서 전체를 뺀다

<!-- kimchi-ignore-start -->
| 나쁜 예 | 좋은 예 |          이 구간만 뺀다
| 얇은 계약 | 낮은 결합도 |
<!-- kimchi-ignore-end -->

얇은 계약이라고 쓴 줄 <!-- kimchi-ignore -->   이 줄만 뺀다
```

이 저장소의 `rules/`와 설계 문서가 그 표시를 쓰고 있습니다. 나머지 한국어 문서는 자기 린터를
통과해야 하고, `npm test`의 `dogfood` 시험이 그것을 확인합니다. 이 README 도 예외가 아닙니다.

</details>

## 규칙을 정하는 원칙

용어를 고를 때 이 순서로 찾습니다.

1. **한국어 기술용어가 있으면 그것.** 대개 한자어입니다. 결합도, 의존성, 응집도, 불변식, 멱등,
   영향 범위, 책임, 경쟁 조건, 교착 상태, 처리량, 지연 시간, 부수 효과, 하위 호환.
2. **정착된 외래어가 있으면 그것.** 캐시, 커밋, 머지, 브랜치, 배포, 인터페이스, 리팩터링, 스레드.
3. **둘 다 없으면 원어를 그대로.**
4. **순우리말 풀어쓰기는 최후 수단.**
5. **은유는 번역 대상이 아니다.**

4번이 가장 자주 어긋납니다. "자연스러운 한국어"는 순우리말을 뜻하지 않습니다. 한국어 기술
문서의 실제 어휘는 한자어 밀도가 높고 그것이 더 짧고 정확합니다.

같은 원문에서 갈리는 두 방향의 실패입니다.

<!-- kimchi-ignore-start -->
| 원문 | ❌ 틀린 답 1 (직역) | ❌ 틀린 답 2 (풀어쓰기) | ✅ 맞는 답 |
|---|---|---|---|
| thin contract | 얇은 계약 | 모듈끼리 서로 알아야 하는 것을 최소로 줄이세요 | 결합도를 낮추세요 |
| blast radius | 블라스트 레디우스 | 여파가 미치는 범위 | 영향 범위 |
<!-- kimchi-ignore-end -->

설계 판단과 그 근거는 [설계 문서](docs/superpowers/specs/2026-09-22-natural-korean-plugin-design.md)에
적어 두었습니다.

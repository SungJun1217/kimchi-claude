# kimchi-claude 설계 — 자연스러운 한국어로 답하는 클로드 코드 플러그인

작성일: 2026-09-22

## 문제

클로드 코드가 한국어로 답할 때 한국 개발자가 실제로 쓰지 않는 말이 나온다. 세 갈래로 갈린다.

1. **직역 신조어** — `thin contract`를 "얇은 계약"으로, `ladder`를 "레더"로 옮긴다. 단어를 하나씩 보면
   한국어인데 뜻이 통하지 않는다.
2. **판교어와 한영 혼용** — "이 컴포넌트의 state를 업데이트하고 디플로이하시죠".
3. **번역체 문장 구조** — "우리는 캐시를 재생성한다", "당신의 코드", "~를 수행하다".

세 갈래가 서로 반대 방향으로 당긴다는 점이 중요하다. 1번은 영어를 너무 많이 옮겨서 생기고 2번은 너무 적게
옮겨서 생긴다. 따라서 "영어를 줄여라" 나 "영어를 써라" 중 어느 쪽도 해법이 아니다. **용어별로 정착된 표기를
고정하는 것** 과 **문체를 고정하는 것**, 두 축으로 접근해야 한다.

## 목표와 비목표

### 목표

- 사용자가 한국어로 물으면 한국 개발자가 실제로 쓰는 말투로 답한다.
- 설치만 하면 켜진다. 사용자도 모델도 무언가를 따로 불러오지 않는다.
- 클로드의 작업 품질은 그대로 유지한다. 판단, 분석, 코드, 도구 사용에 관여하지 않는다.

### 비목표

- 코드 주석과 소스 파일 안의 문자열은 건드리지 않는다. 오픈소스나 다국어 팀에서 역효과가 난다.
- 영어로 진행하는 세션에는 개입하지 않는다.
- 대화 텍스트를 실시간으로 검사하거나 고쳐 쓰지 않는다. 그럴 수 있는 배선이 없다(아래 "알려진 한계" 참조).

## 확정된 결정

| 항목 | 결정 |
|---|---|
| 목표 문체 | 실무 동료체. 존댓말, 군더더기 없음. 같이 일하는 개발자가 슬랙으로 설명해 주는 느낌 |
| 적용 범위 | 대화 설명, 계획서·할 일 목록, 커밋 메시지·PR 설명. 코드 주석 제외 |
| 활성 조건 | 사용자가 한국어로 쓸 때만 |
| 적용 방식 | 플러그인 번들 출력 스타일, `force-for-plugin: true`로 강제 적용 |
| 코딩 지침 | `keep-coding-instructions: true` (필수) |
| 런타임 | Node ESM, 의존성 없음 |

### 용어 처리 우선순위

이 순서가 플러그인의 핵심 규칙이다. 2026-09-26에 소유자가 순서를 뒤집었다 — 아래 "설계 중
뒤집은 결정"에 근거를 남겼다.

1. **한국 개발자가 실제로 타이핑하는 대로 쓴다.** 슬랙, PR, 코드 리뷰에 쓰는 말이 기준이다.
   확신이 서지 않으면 원어(로마자)를 그대로 쓴다.
2. **한국어로 정착한 말은 한국어로 쓴다.** 음차: 배포, 커밋, 브랜치, 머지, 캐시, 빌드, 테스트,
   로그, 업데이트, 리팩터링, 인터페이스, 스레드. 기본 명사: 함수, 배열, 값, 호출, 반환, 설정.
   한자어 기술 용어: 결합도, 응집도, 의존성, 멱등, 동시성, 병목, 직렬화, 캡슐화, 추상화, 인증, 인가.
3. **개발자가 로마자로 쓰는 말은 로마자로 쓴다.** state, props, payload, target, directory,
   endpoint 같은 명사다. race condition·deadlock·latency·throughput·side effect·regression도
   여기 넣는다 — 슬랙·PR에서 개발자가 실제로 영어 원어를 그대로 타이핑하고, 규칙표
   (`rules/hanja.md`, `rules/terms.md`)도 이제 원어를 `쓸 것`의 첫 자리로 가르친다. 경쟁
   조건·교착 상태·지연 시간·처리량·부수 효과·회귀는 설명이 필요할 때 괄호로 덧붙이는 대안이다
   (2026-09-26, 아래 "설계 중 뒤집은 결정"의 뒤이은 항목 참고). function·array·value도
   함수·배열·값이 정착 한국어 명사이므로 로마자로 남기지 않는다. 명사 자리에만 쓰고 동사는
   한국어를 쓰며, 로마자 동사에 하다를 붙이지 않는다(`push합니다`는 틀리고 `푸시합니다`가
   맞다). 사내 은어(컨펌, 어사인, 팔로업)는 기술 용어가 아니므로 여기 해당하지 않는다.
4. **순우리말 풀어쓰기는 최후 수단이다.** 서술문으로 늘이면 대개 더 어색해진다.
5. **은유는 번역 대상이 아니다.** 은유를 벗기고 개념의 이름을 쓴다.

4번과 5번이 특히 중요하다. 이 두 줄은 모델의 기본 성향을 거스르는 지시이므로 다른 규칙보다 강하게 써야 한다.
근거는 아래 "설계 중 뒤집은 결정"에 기록해 두었다.

### 왜 출력 스타일인가

처음 설계는 SessionStart 훅이 규칙을 `additionalContext`로 주입하는 방식이었다. 조사 결과 플러그인이
출력 스타일을 번들로 내보낼 수 있고, `force-for-plugin: true`를 달면 사용자가 고르지 않아도 적용된다는
것을 확인했다. 스타일 본문은 대화 컨텍스트가 아니라 **시스템 프롬프트**에 들어가고 매 요청마다 다시
전송된다.

이것이 훅 주입보다 나은 이유는 세 가지다.

- 컨텍스트 압축으로 사라지지 않는다. `compact` matcher로 재주입할 필요가 없다.
- 긴 세션에서 흐려지지 않는다. 상기용 재주입 훅이 필요 없다.
- 모델의 판단이 개입하지 않는다. 스킬처럼 "열어 볼지" 결정하는 단계가 없다.

이 발견으로 훅 셋 중 둘(`inject-style`, `remind-style`)과 한글 감지 코드, 세션 언어 상태 파일이
모두 사라졌다.

근거(클로드 코드 2.1.278 바이너리 문자열):

```
name                       Style name used in the Output style picker in `/config` and in settings.
description                Shown in the Output style picker in `/config`.
keep-coding-instructions   If true, the default coding instructions stay in the system prompt
                           alongside this style.
force-for-plugin
```

로더 메시지: `Using forced plugin output style:`, `Multiple plugins have forced output styles: ... Using:`,
`Skipping plugin output-style `.

### `keep-coding-instructions: true`가 필수인 이유

기본값은 false다. false면 클로드 코드의 기본 소프트웨어 엔지니어링 지침이 시스템 프롬프트에서 빠진다.
그러면 말투는 좋아지고 작업 실력이 떨어진다. 정확히 피해야 할 결과다. 내장 스타일(Concise, Explanatory)도
모두 `keepCodingInstructions: true`로 정의되어 있다.

### 강제 적용의 대가

`force-for-plugin: true`는 사용자의 출력 스타일 선택을 덮어쓴다. 이 플러그인을 켜면 Concise나
Explanatory를 쓸 수 없다. "설치만 하면 켜진다"가 요구사항이므로 이 대가를 받아들인다. 다른 스타일을
쓰려면 플러그인을 임시로 끄면 된다는 안내를 README에 넣는다.

여러 플러그인이 동시에 강제하면 먼저 로드된 하나만 적용되고 경고가 출력된다.

## 규칙 자료 형식

`rules/*.md`는 모두 같은 표 구조를 쓴다. 사람이 읽는 문서와 기계가 읽는 규칙이 같은 파일이라
두 벌이 어긋날 수 없다.

```markdown
| 원어 | 쓰지 말 것 | 쓸 것 | 이유 | 검사 | 순위 |
|---|---|---|---|---|---|
| thin contract | 얇은 계약 | 낮은 결합도 | 은유 직역, 한국어로 뜻이 안 통함 | 치환 | 핵심 |
| blast radius | 여파가 미치는 범위 | 영향 범위 | 풀어쓰기로 늘어짐 | 치환 | 핵심 |
| your | 당신의 | 이 / 생략 | 영어 your 직역 | 정규식 | 핵심 |
| we | 우리는 ~합니다 | 주어를 빼고 대상을 주어로 | 영어 인칭 주어 직역 | 프롬프트 | 핵심 |
```

- `원어` — 해당 영어 표현. 문장 구조 규칙처럼 대응하는 원어가 없으면 `—`.
- `쓰지 말 것` — `~`는 "앞뒤에 무엇이 붙든"을 뜻한다.
- `순위` — `핵심` / `보통` / `참고`. 스타일 본문 분량을 자르는 기준.

`검사` 열의 세 값이 세 가지 실제 능력에 대응한다. 이 대응이 설계의 핵심이다.

| 값 | 뜻 | 누가 처리하나 |
|---|---|---|
| `치환` | 문자열로 잡히고, 쓸 것으로 그대로 바꿔도 뜻이 상하지 않는다 | 린터가 자동 교정까지 한다 |
| `정규식` | 잡을 수는 있지만 문맥을 봐야 고칠 수 있다 | 린터가 경고만 한다 |
| `프롬프트` | 문자열로 잡을 수 없다 | 출력 스타일만이 막을 수 있다 |

정규식으로 못 잡는 규칙은 예방밖에 방법이 없으므로 스타일 본문에 우선 넣는다.

`toPattern`이 지원하는 것은 리터럴과 `~` 물결 와일드카드뿐이라, "임의의 로마자 동사에
하다 계열 어미가 곧바로 붙는다"처럼 낱말 자체가 아니라 형태를 보는 패턴은 표 한 줄로
못 적는다. `push합니다`, `deploy한`이 이 경우다(0.15.0의 표기 원칙 — 로마자는 명사 자리에만
쓰고, 정착한 음차 동사는 한글로 쓴다 — 를 헤드리스로 돌려 보니 실제로 나왔다). 이런 패턴은
`hooks/lib/latin-hada.mjs`가 별도 엔진으로 찾는다. `rules/` 안에 두지 않는 이유는
`parseTable`이 6칸 표만 규칙으로 읽고 그 밖의 줄은 "형식이 깨진 행"으로 세기 때문이다 —
다른 형식의 표를 섞으면 `corpus.test.mjs`의 `skipped === 0` 검사가 깨진다. 자연스러운
활용형은 문맥마다 다를 수 있어(예: "업데이트합니다" 대 "업데이트해서") 이 발견은 언제나
`정규식`으로 분류되어 경고만 한다.

`lint()`에는 이 검사가 규칙 객체 하나(`LATIN_HADA_RULE`)로 얹힌다. `bad`가 매치마다(동사마다)
달라 규칙표처럼 정적 정규식 하나로 셀 수 없으므로, 이 규칙은 `toPattern(rule.bad)` 대신
`find(masked, normalized)` 매처를 들고 있다 — `lint()`는 규칙에 `find`가 있으면 그 함수를
불러 이미 다 채운 발견 목록을 그대로 받아들인다. 규칙 자체가 자기 검사 방법을 들고 있으므로
lint()의 규칙 순회 루프는 "규칙표 정규식이냐, 그 밖의 매처냐"를 가르지 않는다.

`LATIN_HADA_RULE`은 `overlapFree: true`도 함께 든다 — `lint()`가 규칙끼리 겹치는 발견을
`resolveOverlaps`로 해소할 때, 이 표시가 있는 발견은 그 다툼에서 아예 빠져 규칙과 span이
겹쳐도 서로 밀어내지 않고 **둘 다** 보고한다(같은 표시를 물결표 있는 문장 패턴 규칙도 쓴다 —
`isOverlapFree`가 두 경우를 한 갈래로 본다). 처음에는 규칙과 한 findings 배열에 섞어 넣고
함께 겹침을 해소했는데, "build할때 확인합니다"에서 latin-hada가 잡은 "build할"이 더 길다는
이유로 겹치는 치환 규칙("할때"→"할 때")까지 밀어냈다 — `applyFixes`가 `lint()`의 결과를
그대로 후보로 쓰므로, 지적만 사라지는 게 아니라 원래 되던 자동 교정까지 함께 사라졌다(실측,
0.16.0). latin-hada는 절대 자동 교정하지 않으므로(check가 늘 정규식이다) 규칙과의 겹침은
표시상의 문제일 뿐이라 밀어낼 이유가 없다.

`rules.mjs`의 `loadRules()`는 규칙표(`rules`)와 별도로 `builtins`(`LATIN_HADA_RULE`을 담은
배열)를 함께 내보낸다. 규칙표 자체만 다루는 소비자(`build-style.mjs`, README 규칙 수,
`corpus.test.mjs`의 표 시험, `import-corpus.mjs`)는 `rules`만 그대로 쓰면 이 검사가 섞여
들어오지 않는다 — 스타일 본문에 latin-hada 예시를 실을 수도, README 규칙 수에 셀 수도
없으니 옳다. 실제로 검사하는 전체 집합이 필요한 훅 쪽은 `hooks/lib/artifact.mjs`의
`loadToneRules()`가 `[...rules, ...builtins]`로 이어 붙인다. `rules.mjs`가 `latin-hada.mjs`를
불러오는데 `latin-hada.mjs`도 `검사` 칸 상수(`CHECK_REGEX` 등)가 필요해 거꾸로 `rules.mjs`를
불러오면 순환 참조가 되므로, 그 상수들은 의존성이 없는 `hooks/lib/checks.mjs`로 옮기고
`rules.mjs`는 기존 이름을 그대로 다시 내보낸다(가져다 쓰던 곳을 고칠 필요가 없다).

동사 목록은 일부러 짧다. `import`·`export`·`return`·`delete`는 언어 예약어이고
`fetch`·`load`·`render`는 그 자체로 흔히 참조되는 전역 API·생명주기 메서드 이름이다.
"한 모듈이 상대에게서 import하는 심볼 수"처럼 실제로 관찰된 문장에서 `import`는
표기 위반이 아니라 import 구문 자체를 가리키는 말이었다 — 낱말 하나로는 "구문을
가리키는 용법"과 "번역해야 할 동사 용법"을 가를 수 없어 이 일곱은 뺐다(불변식 5).
`check`(체크박스의 "체크"와 확인의 뜻이 갈린다)와 `pull`("풀하다"라는 정착 음차가
없다, 개발자는 "pull 받아서"처럼 로마자 명사로 남긴다)도 같은 이유로 뺐다. `call`·
`apply`·`reset`도 API 이름으로 쓰이지만 실제 대화에서는 일반 동사 용법이 압도적으로
많아 남겼다 — `hooks/lib/latin-hada.mjs`의 VERBS 주석에 판단 기준을 적어 뒀다.

왼쪽 경계도 낱말 하나만으로는 못 가르는 경우가 있다. "git push하면"·"npm test하면"·
"unit test하는"처럼 명령 이름이나 영어 합성어의 일부일 때는 실제로 관찰된 문장이라도
빼야 한다 — 로마자 낱말 뒤에 공백이 오고 그 뒤에 동사가 바로 이어지면 잡지 않는다(가변
길이 부정 후방탐색, V8이 지원한다). "재commit해야"처럼 한글이 로마자 동사에 공백 없이
바로 붙는 경우는 이 검사 자체가 알 필요가 없다 — `findLatinVerbHada`는 항상
`maskProtected`가 가린 문자열에서 도는데, segment.mjs가 "한글 음절 + 로마자 소문자"
모양을 `타겟Id`류 혼합 식별자로 보고 이미 통째로 가리기 때문이다.

`이유` 칸 맨 앞에 `[표기] `나 `[외래어] `를 붙이면 낱말 경계 검사의 예외를 명시적으로 켠다.
`[표기]`는 왼쪽 경계(앞에 다른 낱말이 붙어 있어도 잡는지)를 빼고, `[외래어]`는 왼쪽·오른쪽을
모두 뺀다(외래어는 표기 종류에 포함된다). "해야합니다"(→"해야 합니다")는 앞에 어떤 동사가
오든 붙여 쓴 것 자체가 틀리고, "데이타"(→"데이터")는 "메타데이타"처럼 다른 외래어에 붙어
있어도 표기가 틀린 건 마찬가지라 이 예외가 필요하다. 표지는 `hooks/lib/rules.mjs`의
`parseTable`이 떼어 `rule.kind`로 넘기고, `hooks/lib/lint.mjs`는 그 필드만 본다 — 예전에는
이유 문장에 "표기"·"외래어" 같은 낱말이 있는지를 정규식으로 봤는데, 이유 문장을 사람이 읽기
좋게 다듬다가 낱말이 우연히 빠지거나 들어가면 판정이 조용히 바뀌었다. 0.13.19에서 실제로
그랬다 — 레지스터리는 이유에서 "외래어"가 빠져 분류를 잃었고, "50 %"는 반대로 새 이유의
"띄어도"에 걸려 없던 분류를 얻었다(둘 다 이번 단위에서 원래 분류로 되돌렸다). 판정과 설명을
분리해 이유는 자유롭게 고쳐도 안전하게 했다.

`검사` 값은 손으로 정하지 않는다. `scripts/import-corpus.mjs`가 계산한다. 규칙이 수백 개면
사람이 판정하다가 반드시 틀린다.

판정 순서는 이렇다.

1. 자료에 `lintable: false`로 표시됐거나 금칙어가 한 글자면 `프롬프트`.
2. 금칙어가 40자를 넘으면 `프롬프트`. 그 문장 하나에서만 걸리므로 린터에 쓸모가 없고,
   스타일 본문의 대조 예시로만 값어치가 있다.
3. 금칙어가 24자를 넘으면 `정규식`. 잡을 수는 있지만 문장을 통째로 갈아 끼우는 것은 위험하다.
4. 대체 표현에 `/`나 "생략" 같은 신호가 있으면 `정규식`. 드롭인이 아니다.
5. 고친 결과가 같은 규칙에 또 걸리면 `정규식`. 순환한다.
6. `applyFixes`로 실제 치환을 해 본다. 되면 `치환`, 안 되면 `정규식`.

2번과 3번의 길이 기준을 쓰는 이유가 있다. 처음에는 "종결어미로 끝나면 예시 문장"이라는
기준을 썼는데 틀렸다. 한국어에서는 구절 단위 패턴도 자연스럽게 종결어미로 끝난다.
"픽스했습니다"는 예시 문장이 아니라 쓸 만한 패턴이다.

### 규칙 자료의 출처

자료는 조사로 모았다. 여섯 분류로 초안을 만들고, 각 초안을 반대편에서 전수 검증하고,
전체를 교차 감사했다. 검증 단계의 최우선 항목은 "대체 표현이 풀어쓰기로 늘어져 어색하지
않은가"였다.

| 단계 | 결과 |
|---|---|
| 초안 | 536개 |
| 전수 검증 | 삭제 6개, 교정 34개. 그중 풀어쓰기 편향으로 고친 것 24개 |
| 교차 감사 | 모순 11건, 위험 항목 12건, 남은 풀어쓰기 편향 17건, 누락 8건 지적 |
| 감사 판정 적용 | 삭제 16개, 교정 18개, 누락 보강 10개 |
| 씨앗 규칙 병합 | 짧고 기계적인 패턴 63개. 조사 자료의 긴 예시 문장을 보완한다 |
| 최종 | 564개 (치환 391, 정규식 71, 프롬프트 102) |
| 낱말 단위 보강 (09-23) | 판교어 29개를 낱말로 추가. 예문 한 줄로 적은 규칙이 부사 하나에 빠져나가던 문제. 모델 문장 20개 적중 3 → 13, 저장소 한글 6만 자에서 오탐 0 |

감사가 잡아낸 것 가운데 특히 값어치가 있던 지적이 셋이다.

- **반대 방향 과교정이 누락되어 있었다.** 규칙집이 한자어 밀도를 계속 올리라고 밀기 때문에
  모델이 공문서체(`본`, `상기`, `~에 대하여`, `~함`)로 튈 위험이 있는데, 그 상한선을 정하는
  항목이 하나도 없었다. 보강했다.
- **기존 한자어를 금지하고 음차를 강요하는 항목이 섞여 있었다.** `배압`→`백프레셔`,
  `상용구`→`보일러플레이트`가 그 예다. 용어 처리 우선순위 1번 위반이고, 이 방향으로 규칙이
  늘면 `캐시`→`임시 저장소`와 대칭인 반대편 사고가 난다. 삭제했다.
- **사물 존대가 빠져 있었다.** `빌드가 완료되셨습니다` 유형은 한국어 출력에서 가장 흔한
  문법 오류인데 항목이 없었다. 보강했다.

교차 감사가 지적한 모순 11건 중 둘은 감사 판정을 적용한 뒤에도 남아 있었고,
`tests/corpus.test.mjs`의 "쓸 것이 다른 규칙에 걸리지 않는다" 시험이 그 둘을 잡았다.
`테일 레이턴시`가 `레이턴시` 금지 규칙에 걸리는 문제와 `플레이키`/`플래키` 표기 분열이었다.
자료가 수백 개로 자라면 이런 순환은 사람 눈으로 못 잡는다.

## 출력 스타일 본문 설계

`scripts/build-style.mjs`가 `rules/`를 읽어 다음 순서로 조립한다. 순서에 의도가 있다.

1. **적용 범위** — 가장 먼저 온다. 품질을 지키는 장치이기 때문이다.
2. **문체** — 규칙 설명 대신 견본 문장 한 쌍.
3. **용어 처리 우선순위** — 위의 다섯 줄.
4. **대조 예시 표** — `핵심` 순위 항목의 `쓰지 말 것 → 쓸 것` 쌍. 설명문이 아니라 표.

적용 범위 절에는 다음 문장이 반드시 들어간다.

> 이 규칙은 사용자에게 보여 주는 문장의 표현에만 적용됩니다. 판단, 분석, 코드 품질, 도구 사용에는
> 영향을 주지 않습니다.
>
> 적용하지 않는 것: 코드, 식별자, 명령어, 파일 경로, 제품·라이브러리 이름, 로그와 오류 메시지 원문,
> 파일에 쓰는 내용, 코드 주석.
>
> 이 규칙 때문에 설명을 줄이거나 분석을 생략하지 마십시오. 담을 내용은 그대로 두고 문장만 다듬는 것입니다.

마지막 문장이 필요한 이유는 "군더더기 없이"를 모델이 "짧게"로 읽을 위험이 있기 때문이다. 표현 규칙이
정보량을 깎는 쪽으로 새는 것을 막아야 한다.

`build-style.mjs`는 출력 길이 상한을 강제한다. 자료가 300개로 자라도 스타일 본문은 상한까지만 담고
`보통`·`참고` 순위부터 잘라낸다. 시스템 프롬프트는 프롬프트 캐시에 올라가므로 비용 부담은 낮지만,
모델의 주의 예산은 여전히 유한하다.

## 린터 (v0.2)

`hooks/guard-artifact.mjs`가 커밋 메시지와 한국어 문서 파일을 검사한다. 대상은 `.md`, `.txt`
같은 문서 확장자뿐이다. 소스 파일을 검사하면 코드 주석까지 건드리게 되고 그것은 적용 범위 밖이다.

| 환경변수 | 기본값 | 훅 | 동작 |
|---|---|---|---|
| (없음) | — | PostToolUse | 위반을 `additionalContext`로 알린다. 클로드가 직접 고친다 |
| `KIMCHI_AUTOFIX=1` | 꺼짐 | PreToolUse | `updatedInput`으로 치환 규칙을 자동 교정한다. 권한 검사는 그대로 거친다 |
| `KIMCHI_BLOCK=1` | 꺼짐 | PreToolUse | `permissionDecision: deny`로 막는다 |
| `KIMCHI_DISABLE=1` | 꺼짐 | — | 아무것도 하지 않는다 |

**기본 동작은 차단도 자동 교정도 아니라 경고다.** 커밋을 문체 때문에 막으면 작업 흐름이 끊기고
재시도 턴을 낭비한다. 문체가 작업을 방해하면 그것은 실패다. 자동 교정도 기본으로 끈다. 도구 입력을
조용히 고쳐 쓰는 것은 놀라움이 크고, 잘못된 규칙 하나가 산출물을 망칠 수 있다.

`updatedInput`은 PreToolUse 훅만 쓸 수 있다. 클로드 코드 2.1.278 바이너리의 훅 출력 명세:

```
- `hookSpecificOutput` - Event-specific output (must include `hookEventName`):
  - `additionalContext` - Text injected into model context
  - `permissionDecision` - "allow", "deny", or "ask" (PreToolUse only)
  - `updatedInput` - Modified tool input (PreToolUse only)
```

### 자동 교정의 조사 문제

한국어에는 치환 고유의 함정이 있다. "얇은 계약**을** 유지"에서 "얇은 계약"을 "낮은 결합도"로
바꾸면 "낮은 결합도**을** 유지"가 된다. 앞말의 받침이 사라졌기 때문이다.

그래서 `hooks/lib/lint.mjs`의 `applyFixes`는 바꾸기 전에 **마지막 음절의 받침 유무가 같은지**
확인하고, 다르면서 뒤에 조사가 붙어 있으면 건너뛴다. 한글 음절은 `(코드 - 0xAC00) % 28`이
0이면 받침이 없으므로 이 판정이 몇 줄로 끝난다. 건너뛴 항목은 경고로 알린다.

### 자동 교정이 permissionDecision을 싣지 않는 이유

`updatedInput`을 돌려줄 때 `permissionDecision: "allow"`를 함께 실었더니 클로드 코드
2.1.282에서 사용자의 권한 프롬프트가 통째로 사라졌다(디버그 로그: "Hook approved tool use for
Bash, bypassing permission prompt"). `git commit -m "타겟 추가" && touch x`가 승인 없이
그대로 실행됐다 — 값이 `"allow"`이기만 해도 사전 승인으로 취급되기 때문이다. `"ask"`도 대안이
아니다. 이미 승인된 도구까지 강제로 다시 묻게 만들어 자동 교정과 무관한 프롬프트를 늘린다.

지금은 `updatedInput`만 돌려주고 `permissionDecision`은 아예 넣지 않는다. 그러면 클로드 코드가
고쳐 쓴 입력을 정상 권한 파이프라인에 그대로 넘기고, 원래 그 도구 호출에 필요했던 승인 절차를
그대로 거친다. 자동 교정이 결정할 일은 "무엇을 바꿀지"이지 "실행을 허가할지"가 아니다.

`systemMessage`는 사용자에게만 보이고 모델에게는 전달되지 않는다는 것도 같은 조사에서 확인했다.
모델이 무엇이 바뀌었는지 모르면 실제로 실행·저장된 내용을 잘못 보고하거나, 되돌리려는 시도로
자동 교정을 무효화할 수 있다. 그래서 `hookSpecificOutput.additionalContext`에도 같은 교정
목록을 실어 모델에게 직접 알린다. `KIMCHI_PII=warn`의 개인정보 경고도 같은 이유로
`additionalContext`를 함께 쓴다 — 경고는 "막지 않는다"는 뜻이지 "모델에게 숨긴다"는 뜻이
아니다.

### 오탐 방어

`hooks/lib/segment.mjs`가 검사 대상에서 코드 블록, 인라인 코드, URL, 파일 경로, 환경변수,
명령행 옵션을 제외한다. `contract`라는 변수명을 "계약"으로 고치라고 하면 재앙이므로 이 부품은
단독으로 테스트한다.

가려낸 구간을 잘라내지 않고 **같은 길이의 센티넬로 덮는다.** 길이를 보존하면 검사에서 찾은 위치가
원문 위치와 1:1로 맞는다.

자바스크립트 정규식의 `\w`와 `\b`가 ASCII만 단어 문자로 보고 한글은 비단어 문자라, 경로와
식별자를 잡는 패턴이 한글 본문을 건드리지 않는다. 경계가 공짜로 생긴다.

한 글자 금칙어(`실`)에는 문자열 검사를 걸지 않는다. 오탐이 너무 많다. 그런 규칙은 스타일 본문으로만
가르친다.

경로·URL·환경변수만으로는 안 막히는 자리가 저장소 전체 903건 말뭉치 실측에서 더 나왔다. 아래
항목을 추가했다. 이런 추가는 항상 양날이다 — 지나치게 넓게 막으면 이번에는 진짜 위반을 놓친다.
각 항목에 그 균형을 어디서 잡았는지, 무엇을 실측했는지 함께 적는다.

**마크다운 링크·이미지 대상.** `[안내](url)`의 `(url)` 부분은 경로이지 산문이 아니다. 대괄호
안(링크 텍스트·대체 텍스트)은 여전히 산문이라 계속 검사한다 — 대상만 가리면 "타겟 안내"라는
링크 텍스트는 그대로 지적할 수 있다. 대상을 무는 문자 집합에서 `(`와 `]`를 뺀다 — `)`만 빼면
닫는 괄호가 없는 `"](".repeat(40000)` 같은 입력에서 `](` 마다 문자열 끝까지 밀었다 되돌리는
이차 비용이 났다(실측 5.7초). 길이도 2000자로 한 번 더 막는다. 참조 정의 줄(`[label]: url
"title"`)은 통째로 코드라 줄 전체를 덮는다.

**참조식 링크의 라벨.** `[글 내용][라벨]`·`[라벨][]`(축약형)·`[라벨]`(단축형)의 라벨은 문서
어딘가의 정의 줄과 글자 그대로 맞아야 링크가 산다. 라벨이 규칙에 걸려 자동 교정되면(예:
타겟→타깃) 정의 줄은 안 바뀐 채 라벨만 바뀌어 `[설정 안내][타깃]`과 `[타겟]:`처럼 죽은 링크가
된다. 문서 안의 정의 라벨을 먼저 모으고(대소문자·공백 정규화), 그 라벨과 글자가 맞는 자리만
가린다. 링크 텍스트(`[글 내용]`)는 라벨이 아니므로 계속 검사한다.

정의는 울타리·인라인 코드를 가린 사본에서 찾는다. `` `[타겟]` `` 처럼 코드로 인용했거나 펜스
안에 예시로 적은 `[타겟]: x`를 진짜 정의로 세면, 그 라벨을 쓰는 모든 자리가 부당하게 검사에서
빠진다.

Edit/MultiEdit은 `new_string` 조각만 본다 — 조각 밖에 있는 정의 줄은 안 보인다. 조각만 보고
판정하면 파일에 `[타겟]:` 정의가 있어도 그걸 모른 채 조각 안의 라벨을 고쳐 죽은 링크를 만든다.
그래서 `hooks/lib/artifact.mjs`가 크기 상한(`MAX_CONTEXT_FILE_BYTES`) 안에서 파일 전체를 읽어
정의 라벨을 모으고, `maskProtected`의 `extraDefs` 인자로 얹는다. 파일을 못 읽으면(새 파일,
크기 초과) `extraDefs`에 `null`을 넘겨 "정의를 알 수 없음"을 표시한다 — 이때는 두 괄호짜리
참조(`][라벨]`·`[라벨][]`)를 정의 확인 없이 보수적으로 전부 가린다. 자동 교정이 죽은 링크를
만드는 쪽이 지적 하나를 놓치는 쪽보다 나쁘다. 단축형(`[라벨]`)까지 넓히지는 않는다 — 혼자서도
흔한 대괄호 표기라 정의 없이 넓히면 오탐이 너무 커진다.

라벨을 무는 문자 집합 `[^\]\n]*`도 위험하다. 정의가 하나라도 있으면 이 정규식들이 문서 전체를
훑는데, 닫히지 않은 `[`가 잔뜩 있는 입력(`"[".repeat(100000)`)에서 시작마다 문자열 끝까지
밀었다 되돌려 36초가 걸렸다(실측). `[^[\]\n]{0,999}`로 대괄호 자체를 문자 집합에서 빼고
길이도 999자로 막는다.

**밑줄 혼합 식별자의 방향.** `content_컨텐츠`처럼 밑줄과 한글이 섞인 식별자를 덮던 패턴이
"밑줄 뒤에 한글이 와야 한다"는 고정 순서를 요구했다. `타겟_id`처럼 한글이 앞에 오면 놓쳤다.
lookahead로 "밑줄과 한글이 어딘가 함께 있다"만 확인하도록 방향을 없앴다.

**한글+로마자 붙임 식별자(`타겟Id`).** 밑줄이 없는 캐멀케이스 혼합은 `\p{L}*`로 양쪽을 넓게
무는 정규식으로 잡으면 137KB 문서에서 마스킹이 0.27ms에서 13.5ms로 50배 느려진다(실측, 불변식
10). 대신 한글→로마자 경계만 찾고 `[\p{L}\p{N}_]` 문자 집합으로 양쪽을 선형으로 넓힌다. 시드를
찾을 때마다 넓힌 뒤 `lastIndex`를 시작 위치에 그대로 두면, "가a"를 5000번 이어 붙인 입력에서
매 시드가 이미 넓혀 둔 구간을 처음부터 다시 훑어 0.5초가 8.8초로 늘어난다 — 넓힌 뒤에는
`lastIndex`를 그 끝으로 밀어 한 붙임 구간을 한 번만 넓히게 한다. 이것과는 별개로, 시드 자체도
"한글+소문자" 또는 "한글+대문자+소문자"(캐멀케이스 시작)로 좁힌다 — `컨텐츠UI를`·`타겟API
호출`·`리팩토링PR을`처럼 한글 뒤에 대문자만 이어지는 두문자어는 식별자가 아니라 산문에 섞인
영문 약어라 계속 검사해야 한다. 반대 방향(`API가`처럼 로마자 뒤에 한글)도 다루지 않는다.

**울타리 없는 셸 프롬프트·로그 줄.** ` ```bash `로 감싸지 않은 `$ npm test`나 `FATAL: connection
refused` 같은 한 줄은 도구 출력이지 산문이 아니다. 줄 시작(공백·인용부호 `> `·목록 표시 허용)
기준으로 그 줄만 덮고, 바로 다음 줄의 설명 문장은 그대로 검사한다. 다만 `Error:`·`Warning:`·
`$ `가 로그 표시가 아니라 한국어 문장의 첫 낱말일 수도 있다 — "Error: 컨텐츠를 불러오지
못하면 다시 시도하세요"는 안내문이지 로그가 아니다. 콜론·공백 뒤 글자 가운데 한글 비율이
30% 이상이면 산문으로 보고 덮지 않고, `$ ` 뒤가 숫자로 시작하면("$ 5를 내면") 프롬프트가
아니라 값을 나타내는 문장으로 본다.

**한 줄짜리 `$(...)` 명령 치환.** 중첩된 괄호까지 정확히 가르려면 bash-commit.mjs 수준의 셸
파서가 필요하다. 문서 산문 안에서는 중첩이 드물어 `[^()\n]*`로 충분히 막는다 — 이 패턴은
처음부터 `(`를 문자 집합에서 뺐으므로 `](...)`와 같은 이차 비용은 나지 않는다.

**울타리 닫힘·ATX 제목 뒤의 들여쓰기.** ` ``` ` 다음 줄이나 `## 제목` 다음 줄에 4칸 들여쓰기가
오면 마크다운은 그것을 새 코드 블록으로 읽는다. 목록 항목 뒤의 들여쓰기(목록 연속)와는 다른
경우라, 울타리·제목 줄을 만나면 "직전 줄이 목록 항목인가" 판정에 쓰는 `lastNonBlankLine`을
비워 목록 연속으로 오판하지 않게 한다.

**YAML 프런트매터.** `---`로 감싼 앞머리는 빌드 도구가 읽는 설정이지 산문이 아니다. 다만
`title`·`description`·`summary`·`excerpt`·`subtitle` 값은 사람이 읽는 문구라 계속 검사한다.
여는 `---` 바로 다음 줄이 빈 줄이 아닌 `key:` 모양(YAML 키)이어야만 프런트매터로 인정한다 —
그렇지 않으면 `---`로 감싼 보통 문단이다. 굵게(`*`)·제목(`#`)으로 시작하는 줄은 키로 보지
않는다 — "**참고**: 컨텐츠를 옮겼습니다."는 콜론이 있어도 강조한 산문이지 YAML 키가 아니다.
목록(`- `)·주석(`#`) 줄은 키가 한 번이라도 나온 뒤에만 값으로 인정한다 — 키 없이 곧장 나오면
"## 변경 사항" 뒤에 목록으로 적은 변경 이력처럼 그냥 마크다운 제목·목록이다.

블록 안에 영문 키가 하나도 없어도 프런트매터로 보지 않는다. 빌드 도구가 읽는 키는 실무에서
거의 항상 영문/숫자다. "참고: 컨텐츠 문서를 옮겼습니다"처럼 키 자리까지 온통 한글이면 YAML이
아니라 "키처럼 보이는 한국어 문장"일 수 있다.

**`로`/`으로`의 오른쪽 경계.** "로"는 조사이기도 하지만 "로그"·"로직"·"로더"·"로컬"·"로드"의
시작이기도 하다. "판박이 코드"(→"보일러플레이트") 규칙이 "판박이 코드로그를"까지 잡아
"보일러플레이트로그를"로 깨졌다. 뒤가 한글이 아니거나(문장 끝) 흔히 그 뒤에 오는 조사
연속(는/도/만/서/써/부터/의/까지/라도/라면/나/요/선/은/야/밖에/조차/마저/든/인/다가)일 때만
진짜 조사로 인정하고, 아니면 이 자리에서 판정을 끝낸다 — 일반화한 활용 연쇄 판정은 하지
않는다. "하"+"니다"처럼 다른 어간·어미 조합까지 건드리면 손해가 더 크다.

**heredoc 종료 표시의 따옴표.** `git commit -F - <<EOF`나 `$(cat <<EOF ...)`처럼 heredoc으로
커밋 메시지를 받을 때, 종료 표시를 따옴표로 감쌌는지가 본문 안 `$(...)`·`${...}`·백틱의
자동 교정 가능 여부를 가른다. 감쌌으면(`<<'EOF'`) 셸이 그 글자를 확장하지 않으므로 고쳐도
안전하지만, 감싸지 않았으면(`<<EOF`) `-m` 값과 같은 정책으로 위험한 문자가 없을 때만
교정한다 — 안 그러면 `$(grep 리팩토링 a.txt)`의 검색어까지 바뀐다.

**.txt 이름 목록 배제.** `.txt` 확장자 자체는 남긴다 — 일반 텍스트로 적은 설계 메모·안내문에도
검사해야 할 산문이 있다. 다만 `CMakeLists.txt`·`requirements*.txt`·`*-requirements.txt`·
`constraints*.txt`·`robots.txt`처럼 이름 자체가 이미 정해진 빌드 도구용 형식인 파일은 말투
검사에서만 뺀다. 개인정보 검사는 `pii.mjs`가 파일 종류와 무관하게 모든 파일에 그대로 돈다.

| `rules.mjs` | 마크다운 표 파싱, 깨진 행을 조용히 버리는지 |
| `lint.mjs` | 규칙마다 양성 사례와 음성 사례 한 쌍씩 |
| `applyFixes` | 받침 판정, 조사 안전장치, 뒤에서부터 고쳐 위치가 어긋나지 않는지 |
| `build-style.mjs` | 순위 컷, 출력 길이 상한, 커밋된 생성물이 최신인지 |
| `guard-artifact.mjs` | heredoc 커밋 메시지 추출, 문서 확장자 필터, 세 환경변수, 망가진 입력 |

`build-style.mjs`의 최신 여부 확인이 중요하다. `rules/`를 고치고 스타일 파일을 다시 생성하지 않으면
자료와 제품이 어긋난다. `npm test`가 `--check`를 먼저 돌려 그것을 막는다.

### 2. 규칙표 정합성 (`tests/corpus.test.mjs`)

규칙이 수백 개로 자라면 사람 눈으로 못 잡는 실패가 생긴다. 코드로 막는다.

| 시험 | 잡으려는 실패 |
|---|---|
| 쓸 것이 다른 규칙에 걸리지 않는다 | A가 권하는 표현이 B의 금칙어인 순환 |
| 치환 규칙은 자기 자신을 다시 잡지 않는다 | 고친 결과를 무한히 다시 지적하는 것 |
| 쓰지 말 것이 중복되지 않는다 | 같은 금칙어에 다른 대체 표현이 붙는 것 |
| 깨끗한 한국어 문장에 아무 규칙도 걸리지 않는다 | 규칙이 너무 공격적이어서 생기는 오탐 |
| 치환 규칙은 실제로 치환할 수 있다 | 치환으로 표시했는데 동작하지 않는 것 |
| 한 글자 금칙어에 문자열 검사를 걸지 않는다 | 오탐 폭발 |

네 번째 시험이 규칙 추가의 브레이크 역할을 한다. 깨끗한 예시 문장 여덟 개 중 하나라도 걸리기
시작하면 새로 넣은 규칙이 너무 공격적이라는 신호다.

### 3. 출력 스타일 적재 확인 (`tests/style-file.test.mjs`)

가장 나쁜 실패를 막는 시험이다. 프런트매터에 모르는 키가 있으면 클로드 코드가
`Skipping plugin output-style` 하고 조용히 건너뛴다. 그러면 플러그인은 설치돼 있는데 아무 일도
하지 않고 아무도 알아채지 못한다.

허용되는 키는 네 개뿐이다: `name`, `description`, `keep-coding-instructions`, `force-for-plugin`.
시험이 그 밖의 키를 거부하고, `keep-coding-instructions: true`와 `force-for-plugin: true`가
켜져 있는지, 그리고 편향을 거스르는 문장들이 본문에 남아 있는지 확인한다.

### 4. 골든 파일

`output-styles/natural-korean.md`를 커밋한다. 규칙 한 줄을 고치면 생성물 diff가 리뷰에 드러난다.
이 플러그인은 프롬프트가 제품이므로 프롬프트 변경이 코드 변경처럼 검토되어야 한다.

### 5. 말투와 품질 평가 (`evals/`)

`claude plugin eval .`로 돌린다. `--ablation`이 기본으로 `with-without`이라 플러그인을 켠 팔과
끈 팔을 모두 돌려 점수 차이를 보고한다. 우리가 보고 싶은 것이 정확히 그 차이다.

| 사례 | 겨냥하는 것 | 기대 |
|---|---|---|
| `tone-paraphrase` | 풀어쓰기 편향. 영향 범위/멱등/경쟁 조건/결합도를 쓰는지 | 켬 > 기준선 |
| `tone-metaphor` | 은유 직역. "얇은 계약" 류 | 켬 > 기준선 |
| `tone-pangyo` | 한영 혼용 | 켬 > 기준선 |
| `tone-translationese` | 번역체 문장 구조 | 켬 > 기준선 |
| `tone-notation` | 외래어 표기 | 켬 > 기준선 |
| `english-passthrough` | 영어로 물으면 영어로 답하는지 | 켬 = 기준선 |
| `quality-preserved` | `forEach` + `async` 버그를 정확히 짚는지 | 켬 = 기준선 |

마지막 두 사례가 첫 다섯 개만큼 중요하다. **말투가 좋아지고 실력이 떨어지면 실패다.**
`quality-preserved`의 점수가 기준선보다 낮으면 스타일 본문이 작업을 방해하고 있다는 뜻이고,
그때는 `MAX_CHARS`를 줄이거나 `순위`를 다시 매겨 본문을 줄여야 한다.

채점기는 `regex`를 먼저 쓴다. 무료이고 판정이 흔들리지 않는다. 목록으로 잡을 수 없는 것(문장 구조,
기술적 정확성)만 `llm` 채점기에 맡긴다.

### 6. 손으로 채점하기 (`scripts/score-response.mjs`)

자격 증명 없이 말투를 재는 도구다. 답변을 표준 입력으로 넣으면 위반 목록과 한글 1000자당 밀도를
알려 준다. `--fix`를 주면 치환 규칙을 적용한 결과를 내보낸다.

```bash
cat 답변.md | node scripts/score-response.mjs
node scripts/score-response.mjs --json 답변.md   # CI 채점용
```

## 두 번째 층 — 한국 개발 현실 지식 (v0.3)

이름이 약속한 것과 실물의 간극을 메운다. `kimchi` 는 "한국어"가 아니라 **"한국"** 을
가리키는데, v0.2 까지는 한국어 말투만 다루었다.

### 스킬에 대한 판단이 뒤집힌 이유

말투 규칙에서는 스킬을 거부했다. 매 문장에 적용되어야 하니 모델의 판단에 맡길 수 없었다.
도메인 지식은 반대다. **인코딩 지식은 인코딩을 건드릴 때만 필요하다.** 필요할 때만 열리는
것이 오히려 맞다.

그래서 한 저장소 안에 정반대 원칙으로 동작하는 두 층이 생겼다.

| 층 | 전달 방식 | 근거 |
|---|---|---|
| 말투 | 출력 스타일(시스템 프롬프트) | 매 문장에 적용되어야 한다 |
| 지식 | 스킬(필요할 때 열림) | 해당 영역을 건드릴 때만 필요하다 |

이 구분을 흐리면 출력 스타일의 6000자 상한이 즉시 터진다. 실측: 스킬 네 개를 더해도
항상 켜져 있는 비용은 설명 네 줄, 약 331토큰이다.

### 산문이 아니라 동작하는 코드를 담는다

설명만 쓰면 클로드가 다시 짜면서 또 틀린다. 검증 가능한 알고리즘은 실제 파일로 두고
`tests/examples.test.mjs` 가 검증한다. 시험이 없으면 스킬은 그냥 주장이다.

### 설명의 절반은 말리는 일이다

지식 층에서 가장 값어치 있는 내용은 "이렇게 하라"가 아니라 "하지 마라"였다.

- 주민등록번호는 2020년 10월부터 뒷자리가 임의 발급이라 체크섬 검증이 통하지 않는다.
  검증하는 코드는 정상 번호를 거부한다. 그래서 `resident-number.mjs` 에 검증 함수를 두지
  않았고, 검증으로 읽히는 이름이 생기지 않도록 시험으로 막았다
- 음력 공휴일은 직접 계산하면 반드시 틀린다. 올바른 답은 공공데이터포털에서 받는 것이다
- 한글 정렬을 자모 분해로 직접 하지 않는다. `localeCompare("ko")` 가 이미 옳다

"이렇게 하라"만 있으면 모델이 틀린 방향으로 부지런해진다. 그래서 모든 스킬에
`자주 틀리는 것` 절을 두고, 그 절이 있는지 시험한다.

### 스킬이 조용히 사라지는 실패

출력 스타일과 같은 종류의 실패가 있다. 프런트매터가 첫 줄부터 시작하지 않으면 클로드 코드가
스킬을 건너뛴다. 실제로 겪었다 — 검사 예외 표시를 프런트매터 앞에 넣어 네 스킬이 모두
깨졌다. `tests/skills.test.mjs` 가 프런트매터 위치, 이름 일치, 설명 품질, 참조하는 예시
파일의 존재를 확인한다.

## 훅을 하나로 합친 이유 (v0.7)

검사가 둘이다. 성격이 정반대라 판정은 따로 두지만 **프로세스는 하나로 합쳤다.**

| | 개인정보 | 말투 |
|---|---|---|
| 대상 | 모든 파일 | 한국어 문서와 커밋 메시지 |
| 기본값 | 차단 | 경고 |
| 근거 | 밀어 버린 번호는 되돌릴 수 없다 | 문체가 작업을 막으면 실패다 |

따로 등록하면 도구 호출마다 Node 프로세스가 하나 더 뜬다. 실측 38ms 이고, 기본 설정에서는
말투 훅이 PreToolUse 에서 바로 빠져나오므로 그 38ms 가 순수 낭비다.
합친 뒤 도구 호출당 훅 비용이 110ms 에서 80ms 로 줄었다.

합치면서 결정 우선순위도 명시됐다. 훅 둘이 각자 `permissionDecision` 을 돌려줄 때 무엇이
이기는지는 클로드 코드 명세에 없다. 지금은 **차단이 이긴다.** 주민등록번호가 들어 있으면
말투는 따질 일이 아니다. 막지 않는 경고는 말투 결과에 얹어 함께 내보낸다. 훅은 한 번만
답할 수 있기 때문이다.

## 말투 규칙에 두 번째 경로를 낸 이유 (v0.9)

출력 스타일 본문에는 분량 상한 때문에 규칙 50개 남짓만 들어간다. 나머지 515개 가운데
치환·정규식은 린터가 잡지만 `프롬프트` 규칙은 아무 일도 하지 않았다.

그래서 `natural-korean-writing` 스킬을 만들어 규칙표 전체를 가리키게 했다.

이것이 "말투는 스킬로 하면 안 된다"는 앞의 판단과 어긋나지 않는다. 그 판단은 **말투를
적용하는 일**에 대한 것이었다. 매 문장에 적용되어야 하니 모델 판단에 맡길 수 없다.
반면 "이 문서 말투 좀 다듬어줘" 같은 **검토 요청**은 정반대다. 그때는 전체 표를 펼쳐
보는 것이 맞고, 평소 대화에서는 열리지 않아야 한다.

중복도 생기지 않는다. 스킬이 `rules/*.md` 를 가리키기만 하므로 같은 파일이 스타일
생성기의 원본이면서 스킬의 참고 자료다.

이 과정에서 스킬 시험의 전제가 좁았던 것도 드러났다. 모든 스킬이 `examples/*.mjs` 를
가리켜야 한다고 단정했는데, 참고용 스킬은 `rules/` 와 `scripts/` 를 가리킨다. 진짜
불변식은 "가리키는 파일이 실제로 있는가" 이므로 그렇게 고쳤다.

## 지식 층을 채운 방법 (v0.10)

스킬을 만들 때 내용을 짜냈다. 그 목록이 실사용에 비해 얼마나 비어 있는지는 몰랐다.
**스킬에 실전 질문을 던지고, 모델이 꺼내는 지식 가운데 스킬에 없는 것을 흡수하는** 방법으로
채웠다.

| 던진 질문 | 모델이 꺼낸, 스킬에 없던 것 |
|---|---|
| 이커머스 주문·배송 | 오픈마켓 안심번호(0504). 스킬이 0505 만 받았다 |
| 관공서 CSV 배치 | 엑셀 수식 주입, 전각 숫자, 앞자리 0 소실 |
| 쿠폰 만료와 월 정산 | 근로자의 날은 은행만 휴무, 반쯤 열린 구간, 배치 시각의 시간대 |
| 본인인증과 관리자 화면 | 접속기록 보관 의무, 마스킹은 서버에서, 조합 단위 판단 |

여덟 가지 모두 **조용히 실패하는 종류**다. 예외를 던지는 결함은 금방 발견되지만 이런
것들은 오래 남는다. 지식 층이 값어치를 내는 자리가 정확히 여기다.

이 방법의 요점은 모델이 아는 것을 스킬로 **고정**하는 것이다. 모델이 운 좋게 꺼내는 것에
의존하면 다음 사용자는 못 받는다. 스킬에 넣으면 확실히 받는다.

절제도 필요하다. 접속기록 보관 기간은 처리 규모와 정보 종류에 따라 달라지므로 숫자를
박지 않고 고시를 확인하라고 적었다. 음력 공휴일을 받아 쓰라고 한 것과 같은 판단이다.
변하는 값을 스킬에 넣으면 낡는다.

## 실물 확인이 코드 읽기보다 잘 잡는다

이번 작업에서 찾은 결함은 대부분 실물 확인에서 나왔다. 코드를 읽어서는 하나도 나오지
않았을 것이다.

| 확인 방법 | 찾은 것 |
|---|---|
| 조사 엔진을 저장소 문서에 돌림 | ㄹ 받침 예외 누락. `1로` 를 `1으로` 로 고치려 했다 |
| 흔한 기술 낱말 29개에 돌림 | 24개를 판정하지 못했다. 목록이 작으면 기능이 없는 것과 같다 |
| 글 검토 스킬을 실제로 씀 | 경로가 사용자 세션에서 맞지 않았다. 개발 환경에서만 우연히 맞았다 |
| 지식 스킬에 실전 질문을 던짐 | 위 표의 여덟 가지 |

그리고 손으로 찾은 것은 시험으로 옮겼다. 같은 것을 두 번 손으로 찾지 않는다.
`tests/dogfood.test.mjs` 가 저장소 문서를 검사하고, `tests/improvement.test.mjs` 가
플러그인을 켜고 끈 답변의 차이를 지킨다.

v0.1이 제품의 대부분이다. 린터는 커밋과 문서에만 걸리고 대화 말투는 건드리지 못한다. 먼저 스타일만
내놓고 실제로 좋아지는지 확인한 다음 린터를 붙이는 것이 순서상 맞다.

## 대규모 시험 캠페인 (v0.13.10~0.13.18)

단위 테스트가 늘어도 실제 입력의 다양성은 따로 잰 적이 없었다. 리뷰어 역할과 실행기(tester) 역할을
나누고, 실제 페이로드로 훅을 직접 구동하고 변이(뜻을 아주 조금 바꾼 입력)를 넣어 보는 방식으로
1,400여 개 사례를 훑었다. 다섯 영역에서 결함이 나왔다 — 훅 출력 신뢰성(큰 출력이 파이프에서
잘리는 문제), 자동 교정의 적용 범위(코드·경로까지 건드리던 것), 규칙 매칭의 정확도(낱말 경계·조사
오판, 뜻을 바꾸는 치환), 개인정보 탐지의 강건성(대시·공백 변형, 보이지 않는 문자), 스킬 예제의
품질(마스킹 누출, 저장소 언어 오판). 각 결함은 회귀 시험으로 먼저 재현한 뒤 고쳤고, 단위마다
`0.13.10`부터 `0.13.18`까지 순서대로 커밋했다.

이 캠페인이 남긴 교훈은 "손으로 찾은 결함은 시험으로 박아 둔다"이다. 같은 결함을 사람이 두 번
찾게 하지 않으려면, 찾을 때마다 회귀 시험을 같이 커밋해야 한다.

### 저작권 제약

국립국어원 자료마다 이용 조건이 다르다.

- 어문 규범·용례 찾기·온라인가나다·다듬은 말은 저작권법 제24조의2에 따른 공공저작물
  자유 이용 대상이다.
- 표준국어대사전·우리말샘은 CC BY-SA 2.0 KR(출처 표시·동일 조건 변경 허락)이다. 출전이
  있는 용례 문장은 원저작자 권리가 남는다.
- 『한눈에 알아보는 공공언어 바로 쓰기』(개정판) PDF는 공공누리 제4유형(비상업적 이용만
  허락, 변경 금지)이다. 원문을 그대로 옮길 수 없어, 규칙표의 이유 칸과 이 문서 모두
  지침의 사실과 원칙만 자기 말로 옮기고 쪽수만 인용한다(예: `rules/register.md`의
  "관계를 뜻하는 간은 의존명사라 띄어 쓴다" 항목).

### 다듬은 말을 통째로 들이지 않는 이유

국립국어원 다듬은 말 목록에서 실제로 확인한 예(국립국어원 누리집 개선 > 다듬은 말,
`corpus/nikl-2026-09-25.json`의 `notImported.다듬은말`에 근거와 함께 남겼다)를 보면 왜
통째로 옮길 수 없는지가 분명하다. 디버깅은 "벌레잡기", 로그인은 "회원 들어가기", 쿠키는
"과자"로 다듬어졌다. 브라우저 쿠키를 "과자"로 바꾸면 뜻 자체가 사라진다. 가장 뚜렷한 사례는
서버(server)다 — 다듬은 말은 "메김 선수"인데, 이는 테니스·배구 같은 스포츠에서 공을 먼저
주는 선수를 가리키는 순화어다. 다듬은 말은 낱말 하나가 아니라 **분야(도메인)별로 따로
조어**되므로, 개발 문서의 서버(컴퓨터)에 기계적으로 적용할 근거가 애초에 없다.

(참고로 캐시·커밋·리팩터링처럼 개발 현장에 굳은 음차어는 조사 시점에 다듬은 말
목록에서 찾지 못했다 — 캐시는 "현금" 뜻의 항목만 있고, 커밋·리팩터링은 등재 자체가 없었다.
그래도 다듬은 말 목록이 앞으로 이런 말에 순화어를 얹는다면, 이미 정착한 전문 용어를 순화어로
강제하는 것은 `용어 처리 우선순위`(정착된 한국어 기술 용어·외래어가 있으면 그것을 쓰고,
순우리말 풀어쓰기는 최후 수단이라는 원칙, `skills/natural-korean-writing/SKILL.md` 참고)를
거스른다 — 방향만 반대일 뿐 `cache`를 `임시 저장소`로 강제하는 것과 같은 종류의 실수가 될
것이다.) 그래서 다듬은 말 목록은 근거 조사에만 참고하고, 개발 현장 관행과 맞을 때만(예:
workshop→워크숍, 위 표기 용례와 다듬은 말 목록이 일치한 경우) 규칙표에 올린다.

### 국립국어원 표기와 실무 관행이 갈리는 낱말

아래 낱말은 국립국어원 표기와 개발 현장 관행이 갈려서 일부러 규칙을 만들지 않았다.
실무 관행 쪽이 이미 넓게 쓰이는데 규칙으로 규범 표기를 강제하면 오탐과 반발만 남긴다
(`rules/register.md` 머리말에도 같은 목록과 이유를 적어 뒀다 — 앞으로 규칙표를 만지는
사람이 "고쳐야 할 오표기"로 착각해 새로 추가하지 않도록). 근거는
`corpus/nikl-2026-09-25.json`의 `notImported.관행과_다른_표기`에 남겼다.

| 국립국어원 표기 | 실무 관행 | 근거 | 비고 |
|---|---|---|---|
| 스냅숏 | 스냅샷 | 용례 찾기, 표준국어대사전(『영상』 뜻) | 실무 관행 쪽으로 굳었다 |
| 칼럼 | 컬럼 | 용례 찾기, 표준국어대사전(신문 칼럼 뜻) | 표제어는 신문 칼럼 뜻이고 데이터베이스 열 뜻이 아니다. 개발자는 데이터베이스 문맥에서 컬럼을 쓴다 |
| 프러시저 | 프로시저 | 표준국어대사전(『정보·통신』 뜻) | 실무 관행 쪽으로 굳었다 |
| 플로 | 플로우 | 용례 찾기 | 실무 관행 쪽으로 굳었다 |
| 리포지터리 | 리포지토리 | 우리말샘 | 0.14.0에서 검토. GitHub 한국어 문서가 리포지토리를 쓴다(단, "저장소"가 더 흔해 병기 권장) |

섬네일(thumbnail)·콘텍스트(context)는 표에 올리지 않았다. 외래어 표기법 원칙(thumbnail의
[θ]는 ㅅ으로, context의 짧은 [ɒ]는 오로 적는다)대로면 이 표기가 나오지만, 조사에서 실제
용례·사전 등재를 확인하지 못했다 — 확인하지 못한 근거로 규칙을 만들지 않는다.

`쉘`→`셸`(외래어 표기 규범)도 규칙으로 만들지 않았다. 한 글자 금칙어는 `toPattern`의 최소
길이(2자) 제한에 걸려 문자열 검사가 애초에 안 되고, 미쉘·쉘(사) 같은 고유명사와도 겹친다
(`rules/register.md` 머리말 참고).

### 번역투 근거 보강 (2026-09-27)

딥리서치 라운드 하나로 번역투 규칙의 근거를 보강했다. 새국어생활 2012 봄호(김순영,
korean.go.kr/nkview/nklife/2012_1/22_0105.pdf), 공공언어 바로 쓰기(2022 개정판,
korean.go.kr의 '일본어 번역 투 삼가기'·'영어 번역 투 삼가기' 절), 국립국어원 온라인가나다
310695(이중 피동 질의응답), Microsoft 한국어 스타일 가이드(4.1.8, 4.1.11), 최유숙의
번역투 논문(어문론집 93권, 2023, KCI)이다. 결과는 두 갈래로 갈렸다.

첫째, `잊혀지다`→`잊히다`, `되어지다`→`되다`(및 활용형)는 새로 규칙표에 올렸다. 되다는
그 자체로 피동이라 '-어지다'를 다시 붙일 이유가 없고, 어느 문맥에서도 뜻이 바뀌지 않아
치환이다. 다만 낱말 하나로는 활용형을 다 덮지 못해(예: `잊혀졌다`가 `잊혀지다` 행에
안 걸린다) 자주 쓰는 활용형마다 행을 따로 뒀다 — `hooks/lib/lint.mjs`의 패턴 엔진은
어간+어미 분석이 아니라 문자열 대조라서, 규칙 자료 쪽에서 활용형을 하나하나 적어 줘야
잡힌다.

둘째, `~에 의해`·`~로부터`·`가지다`류의 번역투는 문맥마다 옳은 대체 표현이 갈린다는 근거를
보강했다. `가지다`(이미 규칙표에 있던 행)는 근거 인용만 추가했다. `~에 의해 결정`·
`~로부터 받았다/들었다`는 이 라운드에서 새로 규칙표에 올린 행이다 — "법에 의하여"는 근거를
뜻하는 정당한 쓰임이고, "위원회에 의해 결정됩니다"를 기계적으로 "위원회로 결정됩니다"로
바꾸면 위원회가 결정한 주체가 아니라 선정된 대상으로 읽혀 뜻이 달라지는 식으로, 행위자가
사람·기관인지 도구·장소인지에 따라 옳은 조사가 갈린다. 국립국어원 스스로도 이런 번역투를
비문이 아니라 "부자연스러울 수 있다"고 본다(온라인가나다 317346, 2025-07) — 그래서 이
갈래는 규칙표에서 늘 정규식(경고)이지 치환이 아니다. 자동 치환은 규칙 하나가 모든 문맥에서
옳을 때만 쓴다는 원칙(불변식 5)과 같은 이유다.

이 라운드에서 살아남지 못한 후보도 있다. `~를 통해`를 전부 `~로`로 바꾸라는 권고,
`가지다`를 전부 `있다`로 바꾸라는 권고는 검증 단계에서 반박됐다(각각 1승 2패, 0승 3패) —
둘 다 문맥에 따라 원문이 더 자연스러운 경우가 있었다. 과공손·문체 혼용(사물 존대 등)과
판교어(컨펌, 어사인) 범위는 이 라운드에서 근거를 찾지 못해 열린 채로 남겨 뒀다.

### 사물 존대와 판교어 근거 (2026-09-27)

번역투 라운드가 열어 둔 두 갈래(과공손·문체 혼용, 판교어)를 딥리서치 2차 라운드로 다시 팠다.

사물 존대는 표준 언어 예절(2011) 경어법 장이 1차 근거다. "주문하신 커피 나오셨습니다",
"품절이십니다", "사이즈가 없으십니다", "포장이세요?"를 사물에 붙인 잘못된 -시-로 명시하고
교정형도 함께 준다. 2026-02 문체부·국립국어원 공공언어 설문에서도 과도한 높임이 개선 필요
1위(93.3%)였다. 다만 같은 자료가 간접 존대("눈이 크시다", "걱정이 많으시다")는 인정하므로,
사물 주어의 -시- 전체를 막는 일반 규칙은 오탐을 낸다(불변식 5). 그래서 "품절이십니다",
"품절이세요", "사이즈가 없으십니다"처럼 고정된 구절만 치환으로 올리고, 구조가 통째로
바뀌는 "포장이세요? → 포장해 드릴까요?"와 어미 패턴 "-(으)실게요"(국립국어원 [바른 공공언어]
영상: 받으실게요·앉으실게요·걸어 보실게요 모두 틀린 예로 든다)는 정규식(경고)에 둔다.
동사마다 교정형이 달라 하나로 못 정하기 때문이다. "선생님 나오셨습니다"처럼 사람이 주어인
문장은 규칙표에 없어 건드리지 않는다.

판교어 쪽은 국립국어원 다듬은 말에서 컨펌(2012-04-16 국어심의회 확정, 확인·확정)과
킥오프 회의(첫 회의·첫 기획 회의)의 공식 근거를 찾았다. 김형배 연구관의 칼럼(한국교육신문,
2015)은 컨펌받다 → 확인받다, 딜레이되다 → 미뤄지다/연기되다/지연되다/지체되다를 구문별로
권한다. 컨펌받다는 남이 검토한 결과를 받는다는 뜻으로 좁혀져 확인받다로 고쳐도 문맥과
관계없이 뜻이 상하지 않아 치환으로 올렸고, 딜레이되다는 의도적으로 미뤘는지(연기) 저절로
늦어졌는지(지연)가 갈려 정규식으로 남긴다. 어사인·싱크 맞추다·팔로업·리마인드·핸들링·
ASAP·얼라인·애자일하게는 이번에도 국립국어원 근거를 찾지 못해 기존 정규식·참고 행 그대로
둔다. 2025-12 다듬은 말이 새로 내놓은 마일스톤·휴리스틱은 GitHub Milestones 등으로 개발
현장에 이미 굳은 명사라 규칙에 넣지 않는다.

### 괄호 뒤 조사는 괄호 앞말을 따른다 (2026-09-27)

개발 문서는 영어 원어를 괄호로 병기하는 관행이 있다("비밀 키 암호 기법(secret key
cryptography)"). 그런데 조사 엔진(`particle.mjs`)은 원래 영어 낱말이나 숫자 바로 뒤에
조사가 붙는 자리만 봤다 — 괄호가 끼면 앞말이 뭔지 모른 채 지나쳤다. NIKL 온라인가나다
(327689, 296978, 302384, 316103)는 이런 자리의 조사가 괄호 **안**이 아니라 괄호 **앞**말을
따른다고 답한다. "기법(secret key cryptography)가"는 "기법"의 받침(ㅂ)을 따라 "이"가 맞고,
괄호 안이 영어든 한글이든 상관없다.

`findParticleErrors`에 닫는 괄호 바로 뒤 조사를 찾는 두 번째 스캔을 더했다. 닫는 괄호에서
여는 괄호를 거슬러 찾고, 그 앞말이 한글이면 종성 코드로, 영어/숫자 낱말이면 기존 발음
사전(`finalSoundOf`)으로 받침을 판정한다. 판정할 수 없으면(불변식 5) 손대지 않는다 — 괄호
안에 괄호가 또 있어 앞말이 어느 괄호의 것인지 모호한 경우, 빈 괄호, 앞말이 순수 숫자(그 자체가
근거 조사에서 다루지 않은 자리), 앞말이 코드로 가려진 경우, 여는 괄호가 줄 맨 앞이라 앞말이
아예 없는 경우가 그렇다.

`lint.mjs`가 이미 `particle.mjs`를 임포트하므로(`particleHeads` 등), 한글 종성 판정에 쓰는
`lint.mjs`의 `finalConsonantClass`를 거꾸로 가져다 쓰면 순환 참조가 생긴다. 상수 네 개(음절
시작·끝 코드, 종성 개수, ㄹ 종성 색인)뿐이라 `particle.mjs`에도 그대로 둬 회로를 끊었다.

## GitHub Action (v0.18.0)

플러그인 훅은 클로드 코드 세션 안에서만 돈다. 하지만 문서·커밋 메시지는 PR 리뷰에서도
지적할 수 있는 대상이다. 저장소 어디서든 `uses: SungJun1217/kimchi-claude@v0`로 켤 수 있는
복합 액션(`action.yml`)을 추가했다. `v0`은 릴리스마다 `release.yml`이 최신 `0.x.y` 태그로
강제 이동시키는 태그다 — 아직 1.0.0이 아니라서 관행적인 메이저 태그(`@v1`)를 못 쓰므로,
`v0`을 그 자리에 대신 둔다.

### 왜 오프라인 스크립트 + `gh` 셸 단계로 나눴는가

불변식 10(훅·스크립트는 네트워크를 열지 않는다)을 액션에도 그대로 지킨다. `scripts/action-lint.mjs`와
`scripts/build-review.mjs`는 로컬 파일만 읽고 로컬 JSON만 쓴다 — PR 변경 파일 목록을 모으고,
커밋 메시지·PR 제목/본문을 가져오고, 결과를 리뷰로 올리는 것은 모두 `action.yml`의 셸 단계가
`gh` CLI로 한다. 이렇게 나누면 두 가지가 따라온다.

- 검사 로직에는 여전히 의존성이 없다. `gh`는 GitHub Actions 러너에 이미 있는 도구이지 이
  저장소가 새로 들이는 npm 패키지가 아니다.
- 검사 로직을 `node scripts/action-lint.mjs`로 로컬에서 그대로 재현할 수 있다. 네트워크
  호출이 검사 결과에 섞여 있으면 CI 밖에서 디버깅할 수 없다.

두 번째 이유가 실제로 값어치를 냈다 — `tests/action-lint.test.mjs`가 자식 프로세스로
`action-lint.mjs`를 직접 구동해서 검증하는데, 네트워크가 섞여 있었다면 이 시험 자체가
자격 증명 없이는 못 돌았을 것이다(evals/의 한계와 같은 문제).

### 판정 로직을 새로 만들지 않은 이유

`action-lint.mjs`는 `hooks/lib/artifact.mjs`의 `extractTargets`를 파일마다 `Write` 도구
호출인 것처럼 그대로 불러 쓴다. 문서 확장자 제한, 빌드 도구용 파일 이름 예외
(`isToneExemptBasename`), 파일 자신의 `kimchi-ignore-file` 선언, 참조식 링크 라벨 수집까지
훅과 똑같은 판정을 거치게 하려는 것이다. 판정을 여기서 다시 적으면 반드시 둘이 어긋난다 —
이 저장소의 다른 모든 판정 로직이 그렇듯, 두 번째 구현은 두 번째 버그를 낳는다.

### suggestion 블록을 `치환`에만 붙이는 이유

GitHub 리뷰 코멘트의 ```suggestion``` 블록은 그 줄 전체를 그대로 대체한다. `치환` 규칙은
`applyFixes`가 실제로 안전하게 갈아 끼운 결과가 있으므로 그 줄을 그대로 제안할 수 있다.
`정규식` 규칙은 문맥을 봐야 고칠 수 있다고 스스로 표시한 규칙이라 — `lint.mjs`의
`autoFixReplacement`가 그런 규칙에는 애초에 대체 문자열을 내주지 않는다 — 제안할 안전한
대체문이 없다. 이 규칙은 지적만 코멘트 본문에 적고 suggestion은 붙이지 않는다.
`hooks/lib/artifact.mjs`의 자동 교정이 같은 이유로 `치환`에만 적용되는 것과 같은 경계다.

### 인라인 코멘트는 diff에 보이는 줄만 달 수 있다

GitHub 리뷰 API는 PR diff에 실제로 나타나는 줄(추가되었거나 문맥으로 보이는 줄)에만 코멘트를
붙일 수 있다. `build-review.mjs`가 `pulls/{n}/files` 응답의 `patch`(unified diff hunk)에서
그 줄 번호 집합을 뽑아, 집합 밖의 지적은 코멘트 대신 리뷰 본문의 "diff 밖에서 찾은 표현"
목록으로 접는다. 지적을 조용히 버리지 않는 것이 핵심이다 — PR이 건드리지 않은 줄이라고
지적 자체가 틀린 것은 아니다.

### 재실행마다 리뷰를 다시 쌓지 않는 방법 — 지문, 스레드 해소, 리뷰 접기

첫 버전은 재실행마다 이전 kimchi 리뷰의 인라인 코멘트를 지우고 새로 올리는 방식이었다.
동작은 했지만 이력이 사라졌다 — 리뷰어가 "이 지적이 지난 커밋에서도 있었나"를 알 방법이
없어졌다. 보안 검토에서 이 방식이 뒤집혔고, 소유자가 재설계를 승인했다.

지금은 지적 하나하나에 **지문(fingerprint)**을 매긴다.

```
sha1(file + "|" + ruleKey + "|" + bad + "|" + lineText.trim())
```

`ruleKey`는 실제로 걸린 문구(`bad`)가 아니라 규칙표의 원본 패턴이다 — 같은 문구를 서로 다른
이유로 잡는 규칙이 있을 수 있어, 어느 규칙이 잡았는지까지 지문에 실어야 재실행마다 같은
지적을 같은 것으로 알아본다. `lineText`는 그 줄의 원문이다 — 문구가 그대로여도 줄 자체가
바뀌면(주변 문맥이 달라지면) 다른 지적으로 본다.

인라인 코멘트마다 이 지문을 숨은 마커로 심는다(`<!-- kimchi-claude-lint:v1 fp=<sha1> -->`,
`scripts/build-review.mjs`의 `fingerprint`/`markerFor`). 재실행할 때 `planReviewActions`가
순수 함수로 판정한다.

- 기존 **스레드 중 아직 열려 있는(해결·낡음 표시가 없는) kimchi 스레드**에서만 지문을
  모은다(`isKimchiThread` + `!isResolved && !isOutdated`, 요구사항 5). 이미 해결되어
  화면에서 접힌 스레드의 지문까지 세면, 그 지적이 되돌리기 커밋 등으로 다시 나타나도
  "이미 지문이 있다"고 오판해 다시 올리지 않는 버그가 된다 — "해결됨"은 "그 자리는
  지금 깨끗하다"는 뜻이지 "다시는 지적하지 않는다"는 뜻이 아니다.
- **스레드를 "kimchi 것"으로 인정하는 기준은 첫 코멘트다.** 스레드의 첫 코멘트가 봇이
  달았고 지문 마커가 있어야 kimchi 스레드다. 사람이 나중에 남긴 답에 우연히 같은
  마커 글자가 섞여 있어도(`isKimchiThread`는 `comments[0]`만 본다) 그 스레드를
  가로채지 않는다.
- 이번에 찾은 지적 가운데 그 집합에 없는 지문만 새로 올린다. 전부 이미 있으면 리뷰 자체를
  올리지 않는다("걸리는 것이 없으면 리뷰도 없다"는 원래 방침의 연장이다). **한 줄에
  지적이 여럿이고 그중 일부만 새로 생겼을 때가 까다롭다** — 이미 활성 스레드가 있는
  지적까지 통째로 다시 올리면 같은 지적이 두 스레드에 중복으로 남는다. `finalizeComment`가
  그룹(같은 줄의 지적들)에서 이미 올라간 지문만 걸러내 마커·목록에서 빼고, **`suggestion`
  블록만은 그룹 전체로 계산한다** — 그 줄에 실제로 적용 가능한 최종 모습은 이미 지적된
  것까지 포함해야 나오기 때문이다. 새 지적만으로 suggestion을 만들면 같은 줄의 다른(이미
  지적됐지만 아직 안 고쳐진) 문제를 놓친 채 "고쳐졌다"고 제안하게 된다.
- 이번에 찾은 지적에 더는 나타나지 않는 지문을 가진 기존 kimchi 스레드는 GraphQL
  `resolveReviewThread`로 접는다 — 지우지 않으므로 "이 자리는 이렇게 지적됐다가
  이렇게 고쳐졌다"는 이력이 PR에 그대로 남는다. 단, **사람이 답을 남긴 스레드는
  자동으로 접지 않는다**(`hasNonBotReply`) — 진행 중인 논의를 봇이 임의로 끝내면 안 된다.
- 새 리뷰를 올릴 때는 이전 kimchi 리뷰를(작성자가 봇이고 본문에 리뷰 마커가 있는 것만)
  GraphQL `minimizeComment(classifier: OUTDATED)`로 접는다 — `PullRequestReview`가
  `Minimizable` 인터페이스를 구현한다는 것을 실제로 확인했다. 리뷰 자체는 `COMMENT`
  이벤트라 GitHub REST API로 지우거나 취소할 수 없지만(`dismissals` 엔드포인트는
  `APPROVED`·`CHANGES_REQUESTED`만 받는다), 접어 두면 PR 화면에서 기본적으로 숨는다.

봇 계정 판정에는 함정이 하나 있다. REST API는 이 봇 로그인을 `github-actions[bot]`으로
주지만, GraphQL은 같은 계정을 `login: "github-actions"`(대괄호 없음) `__typename: "Bot"`로
**다르게** 준다(실측). 리뷰 스레드·리뷰·PR 코멘트 조회를 전부 GraphQL로 하므로, REST 표기만
보고 판정하면 봇 코멘트를 하나도 못 알아본다 — sticky 코멘트가 매번 새로 생기고,
`reviewsToMinimize`가 아무것도 못 찾는 식으로 조용히 깨진다. `isKimchiBot(author)`
하나로 두 표기를 모두 받아, 이 판정을 쓰는 모든 자리(`isKimchiThread`, `hasNonBotReply`,
`reviewsToMinimize`, action.yml의 sticky 코멘트 검색 jq)가 같은 기준을 쓴다.

리뷰 본문은 건수와 sticky 코멘트로의 안내만 담아 짧게 유지한다(`buildReviewBody`) — 자세한
목록(diff 밖 지적, 커밋 메시지, PR 제목·본문, 주민등록번호)은 마커
`<!-- kimchi-claude-lint:summary -->`로 찾는 이슈 코멘트 하나에 둔다(`buildStickyBody`).
이 sticky 코멘트는 findings 유무와 무관하게 **매 실행마다 그 자리에서 갱신**한다 — 걸리는
것이 없어졌으면 "걸리는 표현이 없습니다"로도 갱신된다. 리뷰처럼 여러 개가 쌓일 일이 없다.

이 판정들(`planReviewActions`, `finalizeComment`, `reviewsToMinimize`, `buildLineSuggestion`,
`buildComments`)은 전부 `gh` 호출 없이 순수 함수로 짜여 있다 — 자격 증명 없이도
`tests/action-lint.test.mjs`가 합성 데이터로 검증한다.

### 개인정보가 인라인 코멘트에 실리지 않도록 이중으로 막는다

주민등록번호로 보이는 값이 걸린 문서 줄은 `suggestion` 블록에 절대 올리지 않는다 —
`suggestion`은 그 줄 **전체**를 그대로 되읊는 블록이라, 지적한 용어 하나만 가려서는 부족하다.
`action-lint.mjs`가 줄을 읽는 시점에 `redactText`로 이미 가린 사본만 `lineText`에 담고,
가리기 전/후가 달랐으면 `lineHasPii`를 켠다. `build-review.mjs`의 `buildLineSuggestion`은
이 표시만 보고 그 줄의 제안을 아예 만들지 않는다 — 이미 가려진 문자열을 다시
`findResidentNumbers`로 검사하면 더는 13자리로 안 보여 통과해 버리므로, "가리기 전에 있었는가"
를 직접 표시해 둬야 한다.

파일 경로 자체에 번호가 섞인 경우(`900101-1234567.md`)도 같은 함수(`safeDisplayPath`)로 <!-- kimchi-allow-rrn -->
가린 값만 JSON 출력의 `file` 필드에 싣는다 — annotations의 `file=` 속성, 리뷰 본문의 목록
어디에도 원문 경로가 나타나지 않는다. `safeDisplayPath`는 훅의 `pii.mjs`가 경로에 쓰는
`pathOnly`(대시 구분자만 인정하는 좁은 규칙)를 일부러 쓰지 않는다 — 감지에 쓴 규칙과
가리기에 쓴 규칙이 다르면 "걸렸다고는 했는데 정작 안 가려진" 값이 새 나간다(실제로 있었던
결함이다 — 경로 감지는 기본 규칙을 쓰는데 가리기는 `pathOnly`를 써서, 붙여 쓴 형태·공백
구분 형태가 감지는 되고 가려지지는 않았다). 경로 감지와 가리기를 똑같이 기본 규칙(대시·
공백·구분자 없는 형태까지)으로 맞췄다 — `pathOnly`는 파일명 관례(날짜+일련번호를 붙여 쓴
리포트 파일 등)의 오탐을 줄이려는 규칙인데, 표시용 값이 그런 파일명에서 과하게 가려지는
대가가 주민등록번호를 그대로 보여주는 대가보다 훨씬 싸다.

경로 자체에 번호가 있던 파일은 인라인 리뷰 코멘트를 아예 만들지 않는다(`buildComments`의
`pathHasPii` 분기). 리뷰 코멘트의 `path`는 PR의 실제 파일 경로와 글자 그대로 같아야
하는데(다르면 GitHub API가 리뷰 전체를 422로 거부한다), 그렇다고 가려지지 않은 실제 경로를
그 자리에 쓰면 `safeDisplayPath`가 막으려던 유출이 리뷰 코멘트를 통해 그대로 일어난다.
`action-lint.mjs`는 애초에 실제 경로를 JSON 출력 어디에도 남기지 않는다 — `pathHasPii`가
거짓일 때만(가릴 것이 없어서) `file` 값 자체가 실제 경로와 같으므로, `build-review.mjs`는
그 경우에만 `file`을 PR files API 조회에 쓰고, 참이면 그 지적을 무조건 sticky 요약의
"diff 밖" 목록으로 돌린다.

### 마크다운·워크플로 명령 값 이스케이프

파일 이름이나 지적 문구에 백틱이 섞여 있으면 `mdCode`가 감싸는 백틱 개수를 텍스트 안 최장
연속 백틱보다 하나 더 길게 잡아 스팬이 깨지지 않게 한다(커먼마크 규칙). 코드 스팬 안에서는
`@멘션`도 알림으로 파싱되지 않으므로, 파일 이름·문구를 전부 `mdCode`로 감싸는 것만으로
별도의 멘션 무력화 처리 없이 안전해진다. 워크플로 명령(`::warning file=,line=,col=::`)의
속성 값은 GitHub 문서가 요구하는 다섯 문자(`%`→`%25`, `\r`→`%0D`, `\n`→`%0A`, `:`→`%3A`,
`,`→`%2C`)를 인코딩한다 — 인코딩하지 않으면 파일 이름에 든 콤마·콜론이 다음 속성과 경계를
깨거나, 줄바꿈이 명령 자체를 두 줄로 쪼갠다.

### `fail-on-findings`는 게시가 다 끝난 뒤에 판정한다

`오프라인 검사` 단계가 위반을 찾았다고 그 자리에서 실패(종료 코드 1)해 버리면, GitHub
Actions는 그 뒤의 단계를(`if:`에 `always()`나 `failure()`를 명시하지 않는 한) 전부
건너뛴다 — 리뷰 게시, 스레드 해소, sticky 코멘트 갱신이 통째로 스킵되는 버그였다. 지금은
이 단계가 항상 종료 코드 0으로 끝나고, 실제 판정 결과는 스텝 출력(`exit-code`)에만 남긴다.
맨 마지막에 `if: always()`로 건 단계가 앞선 모든 게시가 끝난 뒤 그 출력을 보고 `fail-on-findings`
를 판정한다. 이 판정은 문서·커밋뿐 아니라 PR 제목·본문·주민등록번호까지 모두 센다 — 처음에는
PR 텍스트 위반을 세지 않아 "카운트에는 잡히는데 실패하지는 않는" 불일치가 있었다.

### PR 헤드 커밋을 직접 지정해서 읽는다

`pull_request` 이벤트의 기본 체크아웃은 base 브랜치를 끌어와 만든 merge 커밋이다. 작업
트리를 그냥 읽으면 PR이 손대지 않은 base 쪽 변경까지 섞여 들어와, 훅이 보고하는 줄 번호가
실제 PR 헤드와 어긋날 수 있다. `action-lint.mjs`는 `--head-sha`를 받으면 작업 트리 대신
`git show <sha>:<path>`로 그 커밋 시점의 내용을 직접 읽는다 — 호출부가 어느 ref를
체크아웃했든 결과가 갈리지 않는다. 얕은 클론이 기본이라 그 커밋 객체가 로컬에 없을 수 있어,
`action.yml`이 먼저 `git cat-file -e`로 있는지 보고 없으면 `git fetch --depth=1`로 그
커밋 하나만 받아 둔다. 리뷰 페이로드의 `commit_id`도 같은 헤드 커밋으로 채운다.

### fork PR·Dependabot PR은 annotations로 내려간다

fork에서 온 PR과 Dependabot이 연 PR은 기본 토큰이 읽기 전용이다 — `head.repo.full_name`이
base 저장소와 다르거나 `github.actor`가 `dependabot[bot]`이면 리뷰 게시를 시도하지 않고
워크플로 로그의 `::warning`/`::error`로만 알린다. 이 판정이 빗나가더라도(조직 설정이 특이한
경우 등) 게시 단계들은 403을 만나면 `set +e`로 감싸 job을 실패시키지 않고 넘어간다 — 리뷰를
못 올리는 것이 job 실패보다는 나은 실패다.

## 오탐·놓친 표현 이슈 자동 확인 (v0.19.0)

`false-positive.yml`·`missed-expression.yml` 이슈 양식은 사람이 신고한 문장을 담는다.
신고를 받고 나서 유지자가 매번 손으로 그 문장을 재현해 보는 일이 반복됐다 — `.github/workflows/triage.yml`이
이슈가 열리거나 수정될 때 그 재현을 대신하고, 결과를 코멘트로 남기고 라벨(`reproduced`/
`not-reproduced`)을 붙인다.

설계 원칙은 GitHub Action과 같다. `scripts/triage-report.mjs`는 오프라인 스크립트로, 이슈
본문 텍스트만 읽어 판정하고 코멘트를 올리거나 라벨을 바꾸는 것은 워크플로의 `gh` 셸 단계가
한다(불변식 10). 판정 로직도 새로 만들지 않는다 — `scripts/action-lint.mjs`의
`findingsForTarget`/`findingsForText`를 그대로 불러 "커밋 메시지" 신고는 커밋 메시지 경로로,
"문서 파일"·"기타" 신고는 문서 경로로 재현한다.

`triage.yml`은 `main`(기본 브랜치, 릴리스된 상태만 남는다)을 명시적으로 체크아웃한다 —
"현재 규칙"은 항상 최신 릴리스 기준이지 `develop`의 진행 중인 변경이 아니다.

"대화 답변(스타일)"으로 신고된 문장은 아예 린트 대상이 아니다 — `hooks/lib/lint.mjs`가 보는
것은 커밋 메시지와 문서 파일뿐이고, 대화는 `output-styles/natural-korean.md`(강제 적용되는
시스템 프롬프트)가 다루는 영역이다. 그래서 이 경로는 린트 결과를 절대 주장하지 않는다.
대신 규칙표에 짝이 되는 `프롬프트` 검사 규칙이 있는지만 본다 — `lint()`는 `치환`·`정규식`만
검사하므로(`SCANNABLE_CHECKS`), `프롬프트` 규칙은 `toPattern`으로 직접 시험한다
(`promptRuleMatches`). 이 경로는 `reproduced`/`not-reproduced` 라벨도 건드리지 않는다 —
린트로 확정할 수 없는 것을 확정된 것처럼 라벨로 못박으면 안 된다.

라벨의 뜻은 두 양식에서 서로 뒤집힌다. false-positive는 지금도 걸리면(`findings`가 있으면)
문제가 남아 있는 것이라 `reproduced`다. missed-expression은 반대로 지금도 안 잡히면(`findings`가
없으면) 여전히 놓치고 있는 것이라 `reproduced`다 — "규칙이 이미 잡는다"는 결과는 오히려
`not-reproduced`(더는 놓치지 않는다)로 본다. `decideLabels`가 템플릿별로 이 반전을 명시적으로
가른다.

규칙 출처 링크(`rules/<file>.md#L<line>`)는 규칙 객체 자체가 아니라 다시 찾아야 한다 —
`lint()`가 내는 위반에는 어느 규칙표 파일에서 왔는지(`source`)가 실리지 않는다(`ruleKey`·
`good`·`check`만 있다). `ownerRuleOf`가 같은 조합으로 `loadToneRules()`가 읽어 둔 원본 규칙
배열에서 다시 찾고, `ruleLocation`이 그 파일을 한 번 더 읽어 `| bad |` 셀이 있는 줄을 찾는다.
표 형식이 달라지거나 파일이 없으면 링크 없이 파일 이름만 보여준다 — 링크를 못 만드는 것이
코멘트 자체를 실패시킬 이유는 아니다.

주민등록번호로 보이는 값은 재현에 쓰기 전에 `redactText`로 가린다 — 신고자가 실제 값을
그대로 붙여 넣었을 가능성을 배제할 수 없고, 훅의 `pii.mjs`와 같은 원칙(어떤 산출물도
원문을 되읊지 않는다)을 이슈 코멘트에도 지켜야 한다. 가린 뒤에는 형식만 맞는 값이 되어
13자리 매치가 사라지므로 재현 결과 자체는 달라지지 않는다. PII가 있었으면 `needs-info`
라벨을 추가하고, 코멘트에 형식만 맞는 가상의 값으로 다시 적어 달라는 안내를 함께 싣는다.

이슈 본문(사용자가 붙여 넣은 문장)은 항상 마크다운 코드 블록·인라인 코드로 감싸 인용한다
— `build-review.mjs`의 `mdCode`와 같은 이유로, 코드 스팬·펜스 안에서는 `@멘션`이 알림으로
파싱되지 않는다. 여러 줄 인용은 내용 안의 최장 backtick 연속보다 하나 더 긴 펜스로 감싼다
(`mdBlock`, `mdCode`와 같은 커먼마크 규칙). 펜스는 레이블과 반드시 다른 줄에 둔다 —
`레이블: ${mdBlock(text)}`처럼 한 줄에 이어 붙이면 펜스가 줄 중간에서 시작해 코드 블록으로
인식되지 않고, 사용자가 넣은 여러 줄 텍스트가 살아 있는 마크다운으로 그대로 렌더링되어
`@멘션`·이미지·헤딩이 실제로 해석되는 결함이었다(실측 — 보안 검토에서 발견). `mdCode`(한 줄
인라인 코드)에 줄바꿈이 섞여 들어와도 같은 문제가 난다 — `<input>` 타입 폼 필드("고친다면")는
웹 UI에서 한 줄만 받지만 API로는 방어적으로 줄바꿈이 올 수 있어, `inlineCode`가 스팬에 넣기
전에 항상 한 줄로 접는다. 인용문·인라인 값 모두 길이를 잘라내고(`MAX_QUOTE_CHARS`,
2,000자 + "…(생략)"), findings 목록도 20건까지만 나열한다(`cappedLines`) — 공개 이슈
코멘트가 유출 건수·인용 길이에 비례해 무한정 커지면 안 된다.

이슈 폼 파싱(`parseIssueForm`)은 GitHub이 폼 필드를 `### 라벨\n\n값`으로 렌더링하고,
`render: text` 항목만 제출 시 ` ``` `펜스로 한 번 더 감싼다는 사실에 기댄다. 펜스 유무와
무관하게, 항목이 아예 빠져도(`_No response_` 포함) 견디게 짰다 — 이슈 양식은 사람이 웹
UI로 채우므로 필드 값에 무엇이 들어올지 스크립트가 통제할 수 없다. 본문은 API로 임의
길이를 보낼 수 있어 `MAX_BODY_CHARS`(65,536자)를 넘는 부분은 아예 읽지 않는다. "### 라벨"
경계를 가르는 정규식도 지연(lazy) 수량자 대신(`/^### (.+?)\s*$/m`은 제목 줄에 공백이 아주
길게 이어지면 되짚기가 늘어 이차 시간이 들었다 — 실측) 탐욕적 문자 클래스(`/^### ([^\n]*\S)[
\t]*$/m`)를 쓴다 — 신뢰할 수 없는 이슈 본문이 그 모양을 그대로 만들 수 있는 서비스거부
경로였다.

`kimchi-allow-rrn`은 저장소 관리자가 자기 문서에 형식만 맞는 예시를 남길 때 쓰는 opt-out이다
(`hooks/lib/pii.mjs`). 신뢰할 수 없는 이슈 제출자가 신고 문장에 그 표시를 붙여 검사를 피하고,
실제 번호가 공개 봇 코멘트에 그대로 실리는 수단으로 쓰면 안 된다 — `findResidentNumbers`/
`redactText`에 `ignoreAllowLine: true`를 새로 받게 하고, `triage-report.mjs`는 이 옵션을
켜서 부른다. 같은 이유로 `action-lint.mjs`도 커밋 메시지·PR 제목·본문(fork PR 기여자가
통제하는 자유 텍스트)에는 이 옵션을 켠다 — 다만 파일 경로·내용은 그대로 둔다. 이 저장소
자신의 문서·규칙표가 형식만 맞는 예시에 그 표시를 정당하게 쓰는 관례라(dogfooding), 파일
스캔까지 끄면 저장소 스스로의 PR에서 오탐이 늘어난다.

### 태그가 아직 없는 커밋의 규칙 출처 링크

규칙 출처 링크의 `ref`는 `package.json`의 현재 버전에서 `v<version>` 태그를 그대로
가정한다. 릴리스 절차(AGENTS.md 참고)는 `develop`을 `main`에 병합한 뒤 `v<version>` 태그를
민다 — 두 동작이 원자적이지 않으므로, 병합 커밋이 `main`에 먼저 올라가고 태그는 뒤이어
푸시되는 아주 짧은 틈이 있다. 그 틈 사이에 이 워크플로가 돌면(예: 그 시점에 이슈가 열리면)
링크는 태그가 생기기 전까지 404다 — GitHub Action의 알려진 한계 목록과 같은 종류의 대가다.

## Claude 봇 워크플로 (v0.20.0)

`claude.yml`(`@claude` 멘션)과 `claude-code-review.yml`(자동 코드 리뷰)은 둘 다 소유자 개인
구독의 OAuth 토큰(`CLAUDE_CODE_OAUTH_TOKEN`)으로 돈다. 이 저장소는 공개 저장소이므로 신뢰
게이트 없이는 누구나 이슈·PR 코멘트나 PR 하나로 소유자의 쿼터를 소모하는 세션을 띄울 수
있다 — 그래서 두 워크플로 모두 `author_association`이 `OWNER`/`MEMBER`/`COLLABORATOR`인
경우에만 돈다. `pull_request_review_comment`·`pull_request_review`는 코멘트/리뷰 자체의
`author_association`을 본다 — PR을 누가 열었는지가 아니라 지금 `@claude`를 부른 사람이
신뢰할 수 있는지가 기준이다.

리뷰 워크플로는 신뢰 게이트를 하나 더 둔다. `pull_request.author_association`으로 PR을 연
사람 자체를 거른다 — PR 코멘트로 부르는 것과 달리 리뷰는 PR이 열리거나 라벨이 붙는 것만으로
자동으로 돈다, 즉 사람이 그 순간 신뢰할 수 있는지 판단할 여지가 없다. fork PR은
`head.repo.full_name != github.repository`로 거른다 — 애초에 시크릿을 못 받으므로 돈다 해도
인증에서 실패하지만, 실패한 세션도 워크플로 로그를 남기고 큐를 차지하므로 미리 거른다.
dependabot·github-actions 같은 bot이 연 PR도 거른다 — 리뷰를 받을 대상이 아니고, 이런 PR의
author_association은 대개 `NONE`이라 위 조건에 이미 걸리지만 의도를 코드에 그대로 남겨 둔다.

리뷰 트리거는 PR을 열거나 밀 때마다(`synchronize`)가 아니라 `ready_for_review`(draft 해제)
아니면 `claude-review` 라벨을 붙였을 때만 돈다. 작업 중인 draft PR에 커밋할 때마다 리뷰
세션이 돌면 아직 리뷰받을 준비가 안 된 코드에 쿼터를 쓰는 셈이다 — 리뷰가 필요한 시점(끝났을
때, 또는 사람이 명시적으로 다시 봐 달라고 라벨을 붙였을 때)에만 돈다. `claude-review` 라벨은
`.github/labels.yml`에 정의해 두고 `gh label create --force`로 만든다(불변식과 같은 이유로
동기화 워크플로는 두지 않는다).

리뷰 워크플로는 `--plugin-dir ${{ github.workspace }}`를 `claude_args`에 얹어 이 저장소
자신(kimchi-claude 플러그인)을 함께 불러온다 — 리뷰 코멘트가 한국어로 나올 때도 항상 켜진
출력 스타일을 그대로 적용받게 하려는 것이다(불변식 3). 공식 `code-review` 플러그인
설정(`plugin_marketplaces`/`plugins`)은 그대로 두고 `claude_args`에만 이어 붙인다 — 두
메커니즘이 다르다: 플러그인 두 개는 `plugins` 입력에 쉼표로 나열하는 것이 아니라, 하나는
마켓플레이스 플러그인으로 다른 하나는 로컬 디렉터리 플러그인으로 각각 다른 입력을 쓴다.

두 워크플로 모두 같은 스레드/PR에서 세션이 겹치지 않게 `concurrency` 그룹을 이슈·PR
번호로 건다 — 겹치면 쿼터를 이중으로 쓰고 봇 코멘트도 뒤섞인다. `@claude` 쪽은
`cancel-in-progress: false`(같은 스레드에 두 번 불러도 앞 세션 답을 잃지 않고 순서대로
처리한다)이고, 리뷰 쪽은 `cancel-in-progress: true`(라벨을 여러 번 떼었다 붙이면 최신
diff만 리뷰하면 되고, 옛 세션을 계속 돌릴 이유가 없다). `timeout-minutes: 30`은 어느
쪽이든 한 세션이 통제 불능으로 길어지는 것을 막는 상한이다.

## 알려진 한계

1. **대화 텍스트는 사후 검사만 가능하다.** 어시스턴트가 말하기 직전에 끼어드는 훅이 없다. Stop 훅으로
   검사하면 사용자는 "어색한 한국어 → 고친 한국어"를 연달아 보게 된다. 그래서 대화 텍스트에 대해서는
   예방(출력 스타일)만 하고 사후 교정은 하지 않는다.
2. **린터는 목록에 있는 것만 잡는다.** 번역체 문장 구조처럼 목록화되지 않는 문제는 출력 스타일에 의존한다.
3. **강제 적용은 다른 출력 스타일을 배제한다.** 위의 "강제 적용의 대가" 참조.
4. **규칙 자료의 품질이 제품의 품질이다.** 배선은 작고 자료가 크다. 잘못된 항목은 도움이 아니라 해가 된다.
5. **개선 증거는 회귀 시험으로만 남아 있다.** `claude plugin eval` 을 돌릴 수 없어,
   플러그인을 켜고 끈 상태로 같은 질문에 받은 실제 답변을 `tests/fixtures/` 에 보존하고
   린터로 채점해 차이를 `tests/improvement.test.mjs` 로 굳혔다. 비교 한 건뿐이고 표본이
   적다. 넓은 측정은 평가 세트가 돌아야 가능하다.
6. **낱말 경계 검사는 붙여 쓴 외래어 복합어를 못 잡는다.** "에러핸들링"·"고객니즈"·
   "코드오너십"·"비즈니스임팩트"·"재디플로이"처럼 판교어가 다른 한글 낱말에 그대로
   붙어 있으면, `lint.mjs`의 왼쪽 경계 검사가 "다른 낱말 속"으로 보고 지적하지 않는다.
   보수적인 쪽을 택했다 — 경계를 느슨히 하면 "디커플링"의 "커플링"처럼 무관한 낱말
   속에서 오탐이 난다. 띄어 쓴 형태("에러 핸들링")는 그대로 잡는다.
7. **평가는 자격 증명이 있는 환경에서만 돌아간다.** `claude plugin eval`은 자식 `claude` 프로세스를
   띄우는데, 그 프로세스가 자격 증명을 물려받지 못하면 모든 사례가 인증 오류로 실패한다. AWS Bedrock
   경유 세션 안에서 특히 그렇다. 사례 파일 자체는 적재되고 `regex` 채점기도 도는 것을 확인했지만,
   실행은 사람이 직접 셸에서 해야 한다. 자격 증명이 필요 없는 검증은 `npm test`에 들어 있다.
8. **GitHub Action은 fork PR·Dependabot PR에서 인라인 코멘트를 못 단다.** 둘 다 기본 토큰이
   읽기 전용이라 `pull-requests: write`가 없다 — 이때는 annotations(워크플로 로그의
   `::warning`)로만 알린다. `COMMENT` 이벤트로 올린 리뷰 자체는 GitHub REST API로 지우거나
   취소할 방법이 없어(`dismissals`는 `APPROVED`·`CHANGES_REQUESTED`만 받는다), 재실행마다
   쌓이는 리뷰는 지우는 대신 GraphQL `minimizeComment`로 접는다 — 위 "GitHub Action" 절
   "재실행마다 리뷰를 다시 쌓지 않는 방법" 참조.
9. **리뷰·PR 대화 코멘트 조회는 최근 100개까지만 본다.** 리뷰 스레드(`reviewThreads`)는
   `gh api graphql --paginate`로 전체를 받아 오지만(gh가 `$endCursor`와
   `pageInfo{hasNextPage endCursor}`를 보고 커서를 자동으로 채워 반복 호출한다), 리뷰
   목록(`reviews`)과 PR 대화 코멘트(`comments`)는 `last:100`(가장 최근 100개)만 조회한다
   — sticky 요약 코멘트와 가장 최근 kimchi 리뷰는 이 액션이 최근에 직접 올린 것이라 항상
   그 범위 안에 있다는 전제다. 리뷰·코멘트가 100개를 훌쩍 넘는 매우 오래 논의된 PR에서
   sticky 코멘트보다 최근에 사람이 단 코멘트가 100개 넘게 쌓이면(극단적인 경우), sticky
   코멘트를 못 찾아 새 이슈 코멘트를 하나 더 만들 수 있다. 스레드 안의 코멘트도 스레드당
   `first:50`까지만 본다 — 한 스레드에 답이 50개 넘게 달리는 것은 거의 없다고 보고
   페이지네이션을 넣지 않았다.

## 설계 중 뒤집은 결정

같은 실수를 반복하지 않기 위해 기록해 둔다.

### 스킬 → 출력 스타일

처음에는 큰 용어집을 스킬에 두고 모델이 필요할 때 열어 보게 하려 했다. 잘못된 설계다. 말투는 매 문장에
적용되어야 하는 규칙이므로 모델의 판단에 맡길 수 없다. 스킬과 슬래시 커맨드를 모두 없앴다.

### "자연스러운 우리말로 풀어쓰기" → "한자어 기술용어 우선"

처음 정한 용어 원칙의 2순위가 "자연스러운 우리말로 풀고 첫 등장에 원어 병기"였다. 이 원칙이 잘못된
결과를 만들어 냈다. 실제로 설계 중에 같은 방향으로 두 번 연속 틀렸다.

| 원문 | 첫 시도 | 두 번째 시도 | 맞는 표현 |
|---|---|---|---|
| thin contract | 얇은 계약 | 모듈끼리 서로 알아야 하는 것을 최소로 줄이세요 | 결합도를 낮추세요 |
| blast radius | — | 여파가 미치는 범위 | 영향 범위 |

두 번째 시도들은 전부 순우리말로 풀어쓴 서술문이다. 문법은 맞지만 어색하다. 한국어 기술 레지스터의
실제 어휘는 한자어 술어이고, 그것이 더 짧고 정확하고 이미 통용된다.

이것은 모델의 체계적 편향으로 보인다. "자연스러운 한국어"라는 지시를 받으면 순우리말 풀어쓰기로 기울고
그 결과가 번역 투로 읽힌다. 따라서 출력 스타일은 이 편향을 **명시적으로 거슬러야** 한다. 풀어쓰기를
최후 수단으로 못박은 4번 규칙이 그 장치다.

### 영어 개발 용어를 강제로 한자어·음차로 옮기던 원칙 → 로마자 원어 허용 (2026-09-26)

용어 처리 우선순위 2번이 "정착된 외래어가 있으면 그것을 쓴다"였고, 그 자리에 없는 개발 용어는
4번(순우리말 풀어쓰기) 앞에 "원어 그대로"가 있었는데도 실제로는 프롬프트 규칙이 `state`
같은 낱말을 억지로 한자어로 옮기라고 가르치고 있었다(`이 컴포넌트의 state를 업데이트합니다`
→ `이 컴포넌트의 상태를 갱신합니다`). `function`·`array`·`value`는 원래도 옳게 한국어(함수·배열·값)를
가르치고 있었으니 건드리지 않는다 — 로마자 허용은 `state`·`props`·`payload`처럼 실제로
정착 한국어 대응이 없는 말에만 해당한다. 소유자가 이 순서를 뒤집었다.
한국 개발자가 실제로 쓰는 문장은 `이 컴포넌트의 state를 업데이트하고 배포합니다. build target
directory에 올릴게요. 배포할 때 확인해야 합니다.`이지 `상태를 갱신하고`, `빌드 타깃 디렉터리`가
아니다 — 후자는 국립국어원 규범 표기이지 슬랙·PR에서 개발자가 타이핑하는 말이 아니다.

새 순위는 "정착 외래어"와 "원어 그대로"를 각각 독립된 목적어 집합으로 명시한다. 배포·커밋처럼
이미 한국어로 읽고 쓰는 말은 한국어로, state·payload·target처럼 개발자가 로마자로 그대로
타이핑하는 말은 로마자로 남긴다. 두 집합을 하나로 뭉뚱그리면 다시 이번 실수로 되돌아간다.
로마자는 명사 자리에만 허용한다(`call합니다`, `deploy한`처럼 동사에 붙이면 여전히 틀리다).
사내 은어(컨펌, 어사인)는 이 허용과 무관하게 애초에 기술 용어가 아니므로 한국어로 쓴다 — 별개의
규칙이다. `rules/pangyo.md`의 `update the component's state`·`call this function` 등 항목을
이 방향으로 뒤집었다.

헤드리스 시험(2026-09-26)에서 측정한 사실이 다음을 고쳤다.

- `push합니다`: 로마자 동사에 하다를 붙이지 않는다는 규칙에 예시가 없어 3회 중 1회가 이렇게
  썼다 → 본문에 `푸시합니다`·`머지합니다`·`업데이트합니다` 예시를 박았다. 이후 7회 중 0회.
- 질문의 타겟·디렉토리·릴리즈를 그대로 따라 썼다: 원칙을 조건 없이 줄였을 때 1회 중 1회.
- 질문에 없는데도 디렉토리를 썼다: 질문 조건부 문장("질문에 …가 적혀 있어도")일 때 1회 중
  1회 — 조건문은 질문에 용어가 아예 없는 경우를 막지 못한다.
  → target·directory는 무조건 로마자를 기본값으로 쓰고, 한글로 적을 때만 타깃·디렉터리로
  고치는 무조건 규칙으로 바꿨다. 이후 헤드리스 4회(따라 쓰기 1회, 먼저 꺼내기 2회, state 1회)
  모두 0회.
- Latin 목록에 `race condition`·`deadlock`·`latency`·`throughput`·`side effect`·
  `regression`이 섞여 있었는데, 이 여섯은 `rules/hanja.md`(경쟁 조건, 교착 상태, 지연 시간,
  처리량, 부수 효과, 회귀)와 `rules/terms.md`의 기존 행이 이미 정착 한국어로 가르치고 있어
  자기모순이었다 → 이번 단위에서는 목록에서 뺐다. 이 여섯을 로마자로 되돌릴지는 규칙 자료를
  다루는 별도 단위에서 판단한다.

### 여섯 용어를 로마자로 되돌림 — 규칙표를 먼저 맞춘 뒤 (2026-09-26)

위 자기모순을 규칙표 쪽에서 해소했다. `rules/terms.md`의 음차 경고 행
(레이스 컨디션·데드락·레이턴시·스루풋·사이드 이펙트·리그레션 → 한자어)을 지우고,
`rules/hanja.md`의 대응 행(경쟁 상황·꽉 막힌 상태 등 풀어쓴 표현 → 한자어)의 `쓸 것`을
원어를 첫 자리로, 한자어를 괄호 대안으로 바꿨다. 두 파일이 서로 다른 방향을 가르치던
자기모순이 없어졌으니 우선순위 3번의 로마자 목록에 이 여섯을 다시 넣었다. `검사` 칸은
치환이던 행(`side effect`, `rules/hanja.md`·`rules/pangyo.md`)만 정규식·프롬프트로
내렸다 — 로마자를 고르는 것은 낱말 선택 판단이라 자동 교정 대상이 아니다(5번 불변식).

### 조어한 한국어 번역 → 원어 (2026-09-26)

`sanity check`·`escape hatch`·`source of truth`·`single source of truth`·
`graceful degradation`·`breaking change`·`dirty flag`·`rate limit`(`rules/terms.md`)와
`sanitization`·`early return`(`rules/hanja.md`)의 `쓸 것`이 억지로 조어한 한국어 번역이었다
(예: `sanity check` → `정상 동작 확인`). `nullable` → `nullable`(`rules/observed.md`, "음차보다
원어가 낫다")과 같은 판단이다 — 개발자는 이 말들을 직역으로 읽지 않고 원어 그대로 쓰거나
음차로 쓴다. 원어를 첫 자리로 바꾸고 조어한 번역은 괄호 대안으로 남겼다.

같은 목록에서 후보로 검토했던 `간접 참조`(indirection)·`락 단위`(lock granularity)·
`장애 유형`(failure mode)·`잘림`(truncation)·`요청 조절`(throttling, 이미 `스로틀링`이
첫 자리)는 그대로 뒀다. OS·네트워크 교과서와 클라우드·SRE 문서에서 흔히 보는 한국어
번역이고, 원어를 그대로 쓰는 사례가 드물어 바꾸면 오히려 1번 원칙(실제로 타이핑하는
대로)에 어긋난다. `공개 API 범위`(API surface)도 그대로 뒀는데, 이건 교과서 출처보다는
"API surface" 자체가 한국어 개발자 사이에서 잘 쓰이지 않는 표현이라는 판단이다 — 근거를
표에 적어 둘 만큼 확실하지는 않으니, 실제로 자주 나오는 표현이 관찰되면 뒤집을 수 있다.

### 은유 층의 발견

실패 유형이 두 층이 아니라 세 층이었다.

1. **단어 층** — `블라스트 레디우스` 같은 음차. 잡기 쉽다.
2. **문장 구조 층** — `우리는 ~한다` 같은 번역체. 정규식으로 일부 잡힌다.
3. **은유 층** — `얇은 계약`. 단어도 한국어고 문법도 맞는데 비유가 영어라서 통하지 않는다.

3번이 가장 잡기 어렵다. 앞의 두 층을 모두 통과하기 때문이다. 게다가 은유마다 정착 여부가 다르다.
`무거운 작업`, `가벼운 라이브러리`, `코드 냄새`, `일급 함수`는 한국어에 뿌리내렸고 `얇다`, `두껍다`,
`깊다`, `평평하다`는 내리지 않았다. 원칙으로 이 구분을 유도할 수 없으므로 `rules/metaphors.md`에
사례를 판정해 둔다.

### 프롬프트 규칙 우선 정렬 → 갈래별 예산 배정

스타일 본문에 담을 규칙을 고를 때 프롬프트 규칙을 먼저 담도록 정렬 기준을 넣었다.
근거는 "치환·정규식 규칙은 린터가 대신 잡아 준다"였다. **틀린 전제였다.**

린터는 커밋 메시지와 문서 파일만 본다. **대화는 보지 못한다.** 그리고 대화가 이 플러그인의
주 무대다. 정렬 기준을 바꾼 결과 본문 39개 중 치환 규칙이 3개로 줄어, 용어 규칙 수백 개가
대화에서 아무 일도 하지 않게 되었다.

지금은 행 예산을 두 갈래로 나눈다. 절반은 프롬프트 규칙(예방밖에 방법이 없는 것), 절반은
치환·정규식 규칙(용어)이 쓴다. 한쪽이 예산을 덜 쓰면 남은 자리를 다른 쪽에 넘긴다.
그리고 한 규칙이 안 들어가도 선택을 멈추지 않는다. 뒤에 오는 짧은 규칙은 아직 들어갈 수 있다.

치환과 정규식 사이에는 우열을 두지 않는다. 둘 다 린터가 잡을 수 있어 서로 앞설 근거가 없고,
순서를 매기면 규칙 파일에 적은 순서만 뒤섞인다.

### 남는 자리 넘기기를 순위 tier가 끝날 때까지 미뤘던 것

"한쪽이 예산을 덜 쓰면 남은 자리를 넘긴다"를 처음에는 전체 규칙을 다 훑은 뒤 한 번에 했다.
문제는 **낮은 순위 규칙이 제 갈래에 자리가 있으면 첫 시도에서 바로 들어가 버린다는 것**이다
— 이건 남는 자리 재시도(anyLane)가 아니라 정상적인 첫 시도 admit이라 순위와 무관하게
일어난다. 실측: `rules/hanja.md`의 핵심 순위 행 몇 개를 고치면서 이유 칸이 조금 길어지자,
같은 핵심 순위인 `lazy evaluation`(metaphors.md, 치환)이 치환 갈래(termLane) 예산을 넘겨
밀려났다. 그런데 그보다 뒤에 처리된 **보통 순위**인 `profiling`(hanja.md, 프롬프트)은
프롬프트 갈래(promptLane) 예산이 아직 남아 있어 첫 시도에서 바로 들어갔고, 그 길이만큼
전체 길이(length)를 먼저 써버렸다. `lazy evaluation`이 나중에 남는 자리(anyLane)를
재시도할 차례가 왔을 때는 이미 자리가 없었다 — 순위가 낮은 규칙이 자기 갈래에 여유가
있다는 이유만으로, 순위가 높지만 다른 갈래가 꽉 찬 규칙보다 먼저 본문 자리를 차지한 것이다.

지금은 순위 tier(핵심 → 보통 → 참고)를 하나씩 끝내면서, 그 tier 안에서 갈래 예산을 넘긴
규칙을 곧바로 남는 자리에 재시도한다. 다음 tier로 넘어가기 전에 현재 tier의 재시도를
모두 마치므로, 낮은 순위가 높은 순위의 재시도 기회를 가로챌 수 없다.

이 사고가 알려주는 것은 두 갈래 예산 분배 자체가 아니라 **본문 길이가 핵심 순위 규칙만으로도
거의 다 찬다는 사실**이다(핵심 순위 문장 구조·프롬프트 규칙만 합쳐도 갈래 예산을 훌쩍
넘는다). 그래서 규칙 하나의 이유 문구를 몇 글자 늘리는 것만으로도 다른 파일의 핵심 규칙이
본문에서 빠질 수 있다 — 알파벳순으로 이 파일보다 뒤에 오는 파일(`patterns.md`,
`register.md`, `terms.md`)일수록 더 취약하다. `tests/build-style.test.mjs`에 본문에 반드시
있어야 하는 핵심 규칙 몇 개(문장 구조·은유 대표 사례)를 못박아 뒀다 — 이 시험이 실패하면
새로 늘어난 글자 수만큼 근처 규칙의 이유를 줄여 자리를 돌려줘야 한다.

### 조사 안전장치를 한쪽만 막았던 것

`isParticleSafe`가 매치 **뒤** 글자만 봤다. 그런데 대체 표현이 `를 처리`처럼 조사로 시작하면
매치 **앞** 단어의 받침이 조사를 결정한다. 그래서 `파일에 대한 처리를 진행`이
`파일를 처리`로 바뀌었다. 조사는 양쪽에서 온다.

지금은 대체 표현이 조사로 시작하면 자동 교정을 포기한다. 규칙 표에는 앞말의 받침 정보가 없다.

### 드롭인 판정이 괄호와 쉼표를 놓쳤던 것

`정상 종료 (안전 종료)`나 `결합도, 느슨한 결합`은 규칙 표에서는 대안 나열이지만 본문에 그대로
꽂으면 문장이 망가진다. 실제로 `커플링을 낮췄습니다`가 `결합도, 느슨한 결합을 낮췄습니다`로
바뀌었고, `~을 할 수 있습니다`처럼 물결표가 든 대체 표현은 `이 기능은 을 할 수 있습니다`를
만들었다.

지금은 대체 표현에 괄호·쉼표·슬래시가 있거나, 가운데 물결표가 있거나, 조사로 시작하면
`정규식`으로 내려 경고만 한다. 이 판정으로 치환 규칙이 395개에서 294개로 줄었다.

### 시험 탐침이 조사 인접 상황을 재지 않았던 것

`치환 규칙은 실제로 치환할 수 있다` 시험이 `앞말 ${bad} 뒷말`처럼 양쪽을 띄운 문장만
탐침으로 썼다. 그래서 조사가 바로 붙는 상황을 구조적으로 재지 못했다. 생성기도 같은 탐침으로
`검사` 값을 정했으므로, 생성기와 시험이 같은 맹점을 공유했다. 잘못된 치환 규칙 76개가
시험을 전부 통과한 채로 배포된 이유다.

지금은 `${bad}을`, `${bad}를`, `${bad}이`, `${bad}가` 네 가지 탐침을 쓰고, 교정이 적용되면
대체 표현의 받침이 원래 표현과 같은지 확인한다. 데이터 불변식(대체 표현이 조사로 시작하지
않는다, 괄호·쉼표가 없다)도 따로 시험한다.

### 차단 → 경고

린터의 기본 동작을 차단으로 설계했다가 경고로 내렸다. "클로드의 퀄리티는 유지"라는 제약이 들어오면서
판단이 바뀌었다. 커밋을 문체 때문에 막으면 작업 흐름이 끊기고 재시도 턴을 낭비하며 최악의 경우 원래
하려던 일을 잊는다.

### 검사 두 값 → 세 값

`검사` 열을 `정규식`과 `프롬프트` 두 값으로 설계했다. 그런데 훅 출력 명세에서 `updatedInput`을
발견했다. PreToolUse 훅이 도구 입력을 직접 고쳐 쓸 수 있다는 뜻이고, 그러면 린터가 경고만 하는 것이
아니라 결정론적으로 교정할 수 있다.

능력이 셋이 되었으므로 값도 셋이 되어야 했다. `치환`(자동 교정 가능), `정규식`(경고만),
`프롬프트`(스타일만). 세 값이 세 능력에 정확히 대응한다.

그런데 치환에는 한국어 고유의 함정이 있었다. 조사다. 위의 "자동 교정의 조사 문제" 참조.
이 함정 때문에 `치환` 여부를 사람이 손으로 정하면 안 된다는 결론이 나왔고, `import-corpus.mjs`가
실제 치환을 해 보고 계산하도록 만들었다.

### 자동 교정·경고에 permissionDecision을 실었던 것

`updatedInput`이나 `KIMCHI_PII=warn` 경로 모두 처음에는 `permissionDecision: "allow"`를
함께 돌려줬다. "이미 검사를 통과했으니 명시적으로 허용해 준다"는 생각이었다. 실제 세션에서
확인해 보니 틀린 생각이었다 — 클로드 코드 2.1.282는 `"allow"`를 받으면 사용자의 권한 프롬프트
자체를 건너뛴다. 자동 교정을 켠 상태에서 `git commit`이 사용자 승인 없이 실행됐다.

지금은 두 경로 모두 `permissionDecision`을 아예 넣지 않는다. 결정은 정상 권한 파이프라인에
맡기고, 훅은 `updatedInput`(무엇이 바뀌었는지)과 `additionalContext`(모델에게 알리는 채널)로만
말한다. 자세한 내용은 위 "자동 교정이 permissionDecision을 싣지 않는 이유" 참조.

### 규칙 자료를 손으로 쓰려던 계획 → 조사로 모으고 검증하기

설계 중에 같은 방향으로 두 번 연속 틀린 뒤, 규칙 자료를 손으로 쓰는 것을 포기했다. 대신 분류별로
초안을 만들고, 각 초안을 반대편에서 검증하고, 전체를 교차 감사하는 과정을 거쳤다. 검증 단계의
최우선 항목은 "쓸 것이 풀어쓰기로 늘어져 어색하지 않은가"였다. 실제로 분류마다 다섯에서 여섯 건이
그 이유로 교정되었다.

# kimchi-claude 설계 — 자연스러운 한국어로 답하는 클로드 코드 플러그인

작성일: 2026-09-22

## 문제

클로드 코드가 한국어로 답할 때 한국 개발자가 실제로 쓰지 않는 말이 나온다. 세 갈래로 갈린다.

1. **직역 신조어** — `thin contract`를 "얇은 계약"으로, `ladder`를 "레더"로 옮긴다. 단어를 하나씩 보면
   한국어인데 뜻이 통하지 않는다.
2. **판교어와 한영 혼용** — "이 컴포넌트의 state를 업데이트하고 디플로이하시죠".
3. **번역체 문장 구조** — "우리는 캐시를 재생성한다", "당신의 코드", "~를 수행하다".

세 갈래가 서로 반대 방향으로 당긴다는 점이 중요하다. 1번은 영어를 너무 많이 옮겨서 생기고 2번은 너무 적게
옮겨서 생긴다. 따라서 "영어를 줄여라" 나 "영어를 써라" 중 어느 쪽도 해법이 아니다. **용어별로 정착된 표기를
고정하는 것** 과 **문체를 고정하는 것**, 두 축으로 접근해야 한다.

## 목표와 비목표

### 목표

- 사용자가 한국어로 물으면 한국 개발자가 실제로 쓰는 말투로 답한다.
- 설치만 하면 켜진다. 사용자도 모델도 무언가를 따로 불러오지 않는다.
- 클로드의 작업 품질은 그대로 유지한다. 판단, 분석, 코드, 도구 사용에 관여하지 않는다.

### 비목표

- 코드 주석과 소스 파일 안의 문자열은 건드리지 않는다. 오픈소스나 다국어 팀에서 역효과가 난다.
- 영어로 진행하는 세션에는 개입하지 않는다.
- 대화 텍스트를 실시간으로 검사하거나 고쳐 쓰지 않는다. 그럴 수 있는 배선이 없다(아래 "알려진 한계" 참조).

## 확정된 결정

| 항목 | 결정 |
|---|---|
| 목표 문체 | 실무 동료체. 존댓말, 군더더기 없음. 같이 일하는 개발자가 슬랙으로 설명해 주는 느낌 |
| 적용 범위 | 대화 설명, 계획서·할 일 목록, 커밋 메시지·PR 설명. 코드 주석 제외 |
| 활성 조건 | 사용자가 한국어로 쓸 때만 |
| 적용 방식 | 플러그인 번들 출력 스타일, `force-for-plugin: true`로 강제 적용 |
| 코딩 지침 | `keep-coding-instructions: true` (필수) |
| 런타임 | Node ESM, 의존성 없음 |

> 고쳤고, 테스트는 전부 통과합니다.

### 용어 처리 우선순위

이 순서가 플러그인의 핵심 규칙이다.

1. **한국어 기술용어가 있으면 그것을 쓴다.** 대개 한자어다. 결합도, 의존성, 응집도, 불변식, 멱등,
   영향 범위, 책임, 경쟁 조건, 교착 상태, 처리량, 지연 시간, 부수 효과, 하위 호환.
2. **정착된 외래어가 있으면 그것을 쓴다.** 캐시, 커밋, 머지, 브랜치, 배포, 인터페이스, 리팩터링, 스레드.
3. **둘 다 없으면 원어를 그대로 쓴다.** 억지로 옮기지 않는다.
4. **순우리말 풀어쓰기는 최후 수단이다.** 서술문으로 늘이면 대개 더 어색해진다.
5. **은유는 번역 대상이 아니다.** 은유를 벗기고 개념의 이름을 쓴다.

4번과 5번이 특히 중요하다. 이 두 줄은 모델의 기본 성향을 거스르는 지시이므로 다른 규칙보다 강하게 써야 한다.
근거는 아래 "설계 중 뒤집은 결정"에 기록해 두었다.

### 왜 출력 스타일인가

처음 설계는 SessionStart 훅이 규칙을 `additionalContext`로 주입하는 방식이었다. 조사 결과 플러그인이
출력 스타일을 번들로 내보낼 수 있고, `force-for-plugin: true`를 달면 사용자가 고르지 않아도 적용된다는
것을 확인했다. 스타일 본문은 대화 컨텍스트가 아니라 **시스템 프롬프트**에 들어가고 매 요청마다 다시
전송된다.

이것이 훅 주입보다 나은 이유는 세 가지다.

- 컨텍스트 압축으로 사라지지 않는다. `compact` matcher로 재주입할 필요가 없다.
- 긴 세션에서 흐려지지 않는다. 상기용 재주입 훅이 필요 없다.
- 모델의 판단이 개입하지 않는다. 스킬처럼 "열어 볼지" 결정하는 단계가 없다.

이 발견으로 훅 셋 중 둘(`inject-style`, `remind-style`)과 한글 감지 코드, 세션 언어 상태 파일이
모두 사라졌다.

근거(클로드 코드 2.1.278 바이너리 문자열):

```
name                       Style name used in the Output style picker in `/config` and in settings.
description                Shown in the Output style picker in `/config`.
keep-coding-instructions   If true, the default coding instructions stay in the system prompt
                           alongside this style.
force-for-plugin
```

로더 메시지: `Using forced plugin output style:`, `Multiple plugins have forced output styles: ... Using:`,
`Skipping plugin output-style `.

### `keep-coding-instructions: true`가 필수인 이유

기본값은 false다. false면 클로드 코드의 기본 소프트웨어 엔지니어링 지침이 시스템 프롬프트에서 빠진다.
그러면 말투는 좋아지고 작업 실력이 떨어진다. 정확히 피해야 할 결과다. 내장 스타일(Concise, Explanatory)도
모두 `keepCodingInstructions: true`로 정의되어 있다.

### 강제 적용의 대가

`force-for-plugin: true`는 사용자의 출력 스타일 선택을 덮어쓴다. 이 플러그인을 켜면 Concise나
Explanatory를 쓸 수 없다. "설치만 하면 켜진다"가 요구사항이므로 이 대가를 받아들인다. 다른 스타일을
쓰려면 플러그인을 임시로 끄면 된다는 안내를 README에 넣는다.

여러 플러그인이 동시에 강제하면 먼저 로드된 하나만 적용되고 경고가 출력된다.

## 규칙 자료 형식

`rules/*.md`는 모두 같은 표 구조를 쓴다. 사람이 읽는 문서와 기계가 읽는 규칙이 같은 파일이라
두 벌이 어긋날 수 없다.

```markdown
| 원어 | 쓰지 말 것 | 쓸 것 | 이유 | 검사 | 순위 |
|---|---|---|---|---|---|
| thin contract | 얇은 계약 | 낮은 결합도 | 은유 직역, 한국어로 뜻이 안 통함 | 치환 | 핵심 |
| blast radius | 여파가 미치는 범위 | 영향 범위 | 풀어쓰기로 늘어짐 | 치환 | 핵심 |
| your | 당신의 | 이 / 생략 | 영어 your 직역 | 정규식 | 핵심 |
| we | 우리는 ~합니다 | 주어를 빼고 대상을 주어로 | 영어 인칭 주어 직역 | 프롬프트 | 핵심 |
```

- `원어` — 해당 영어 표현. 문장 구조 규칙처럼 대응하는 원어가 없으면 `—`.
- `쓰지 말 것` — `~`는 "앞뒤에 무엇이 붙든"을 뜻한다.
- `순위` — `핵심` / `보통` / `참고`. 스타일 본문 분량을 자르는 기준.

`검사` 열의 세 값이 세 가지 실제 능력에 대응한다. 이 대응이 설계의 핵심이다.

| 값 | 뜻 | 누가 처리하나 |
|---|---|---|
| `치환` | 문자열로 잡히고, 쓸 것으로 그대로 바꿔도 뜻이 상하지 않는다 | 린터가 자동 교정까지 한다 |
| `정규식` | 잡을 수는 있지만 문맥을 봐야 고칠 수 있다 | 린터가 경고만 한다 |
| `프롬프트` | 문자열로 잡을 수 없다 | 출력 스타일만이 막을 수 있다 |

정규식으로 못 잡는 규칙은 예방밖에 방법이 없으므로 스타일 본문에 우선 넣는다.

`검사` 값은 손으로 정하지 않는다. `scripts/import-corpus.mjs`가 `applyFixes`로 실제 치환을
해 보고 되는 것만 `치환`으로 표시한다. 규칙이 수백 개면 사람이 판정하다가 반드시 틀린다.

## 출력 스타일 본문 설계

`scripts/build-style.mjs`가 `rules/`를 읽어 다음 순서로 조립한다. 순서에 의도가 있다.

1. **적용 범위** — 가장 먼저 온다. 품질을 지키는 장치이기 때문이다.
2. **문체** — 규칙 설명 대신 견본 문장 한 쌍.
3. **용어 처리 우선순위** — 위의 다섯 줄.
4. **대조 예시 표** — `핵심` 순위 항목의 `쓰지 말 것 → 쓸 것` 쌍. 설명문이 아니라 표.

적용 범위 절에는 다음 문장이 반드시 들어간다.

> 이 규칙은 사용자에게 보여 주는 문장의 표현에만 적용됩니다. 판단, 분석, 코드 품질, 도구 사용에는
> 영향을 주지 않습니다.
>
> 적용하지 않는 것: 코드, 식별자, 명령어, 파일 경로, 제품·라이브러리 이름, 로그와 오류 메시지 원문,
> 파일에 쓰는 내용, 코드 주석.
>
> 이 규칙 때문에 설명을 줄이거나 분석을 생략하지 마십시오. 담을 내용은 그대로 두고 문장만 다듬는 것입니다.

마지막 문장이 필요한 이유는 "군더더기 없이"를 모델이 "짧게"로 읽을 위험이 있기 때문이다. 표현 규칙이
정보량을 깎는 쪽으로 새는 것을 막아야 한다.

`build-style.mjs`는 출력 길이 상한을 강제한다. 자료가 300개로 자라도 스타일 본문은 상한까지만 담고
`보통`·`참고` 순위부터 잘라낸다. 시스템 프롬프트는 프롬프트 캐시에 올라가므로 비용 부담은 낮지만,
모델의 주의 예산은 여전히 유한하다.

## 린터 (v0.2)

`hooks/guard-artifact.mjs`가 커밋 메시지와 한국어 문서 파일을 검사한다. 대상은 `.md`, `.txt`
같은 문서 확장자뿐이다. 소스 파일을 검사하면 코드 주석까지 건드리게 되고 그것은 적용 범위 밖이다.

| 환경변수 | 기본값 | 훅 | 동작 |
|---|---|---|---|
| (없음) | — | PostToolUse | 위반을 `additionalContext`로 알린다. 클로드가 직접 고친다 |
| `KIMCHI_AUTOFIX=1` | 꺼짐 | PreToolUse | `updatedInput`으로 치환 규칙을 자동 교정한다 |
| `KIMCHI_BLOCK=1` | 꺼짐 | PreToolUse | `permissionDecision: deny`로 막는다 |
| `KIMCHI_DISABLE=1` | 꺼짐 | — | 아무것도 하지 않는다 |

**기본 동작은 차단도 자동 교정도 아니라 경고다.** 커밋을 문체 때문에 막으면 작업 흐름이 끊기고
재시도 턴을 낭비한다. 문체가 작업을 방해하면 그것은 실패다. 자동 교정도 기본으로 끈다. 도구 입력을
조용히 고쳐 쓰는 것은 놀라움이 크고, 잘못된 규칙 하나가 산출물을 망칠 수 있다.

`updatedInput`은 PreToolUse 훅만 쓸 수 있다. 클로드 코드 2.1.278 바이너리의 훅 출력 명세:

```
- `hookSpecificOutput` - Event-specific output (must include `hookEventName`):
  - `additionalContext` - Text injected into model context
  - `permissionDecision` - "allow", "deny", or "ask" (PreToolUse only)
  - `updatedInput` - Modified tool input (PreToolUse only)
```

### 자동 교정의 조사 문제

한국어에는 치환 고유의 함정이 있다. "얇은 계약**을** 유지"에서 "얇은 계약"을 "낮은 결합도"로
바꾸면 "낮은 결합도**을** 유지"가 된다. 앞말의 받침이 사라졌기 때문이다.

그래서 `hooks/lib/lint.mjs`의 `applyFixes`는 바꾸기 전에 **마지막 음절의 받침 유무가 같은지**
확인하고, 다르면서 뒤에 조사가 붙어 있으면 건너뛴다. 한글 음절은 `(코드 - 0xAC00) % 28`이
0이면 받침이 없으므로 이 판정이 몇 줄로 끝난다. 건너뛴 항목은 경고로 알린다.

### 오탐 방어

`hooks/lib/segment.mjs`가 검사 대상에서 코드 블록, 인라인 코드, URL, 파일 경로, 환경변수,
명령행 옵션을 제외한다. `contract`라는 변수명을 "계약"으로 고치라고 하면 재앙이므로 이 부품은
단독으로 테스트한다.

가려낸 구간을 잘라내지 않고 **같은 길이의 센티넬로 덮는다.** 길이를 보존하면 검사에서 찾은 위치가
원문 위치와 1:1로 맞는다.

자바스크립트 정규식의 `\w`와 `\b`가 ASCII만 단어 문자로 보고 한글은 비단어 문자라, 경로와
식별자를 잡는 패턴이 한글 본문을 건드리지 않는다. 경계가 공짜로 생긴다.

한 글자 금칙어(`실`)에는 문자열 검사를 걸지 않는다. 오탐이 너무 많다. 그런 규칙은 스타일 본문으로만
가르친다.

## 품질 보호 장치

말씀된 "퀄리티는 유지" 요구를 지키는 장치를 한자리에 모았다.

| 장치 | 막는 실패 |
|---|---|
| `keep-coding-instructions: true` | 코딩 지침이 시스템 프롬프트에서 빠지는 것 |
| 스타일 본문 길이 상한 | 주의 예산을 먹어 작업 정확도가 떨어지는 것 |
| 적용 배제 목록 명시 | 코드·식별자·로그를 한국어로 건드리는 것 |
| "정보량 줄이지 말 것" 문장 | 문체 규칙이 설명 부실로 번역되는 것 |
| 경고 기본, 차단 선택 | 문체 때문에 작업 흐름이 끊기는 것 |
| 훅 실패 시 종료 코드 0, 빈 출력 | 훅이 깨져서 세션이 막히는 것 |
| `KIMCHI_DISABLE=1` 킬 스위치 | 문제가 생겼을 때 빠져나갈 길이 없는 것 |
| `segment.mjs` 구간 제외 | 코드 식별자 오탐 |

훅 실패 처리를 특히 강조한다. 이 플러그인은 말투를 다듬는 부가 기능이고 작업에 필요한 부품이 아니다.
어떤 오류가 나도 조용히 아무 일도 하지 않고 넘어가야 한다.

## 검증

### 1. 단위 테스트 (`node:test`, 의존성 없음)

| 대상 | 확인할 것 |
|---|---|
| `segment.mjs` | 코드 블록·인라인 코드·URL·경로 제외. `contract`가 변수명일 때 안 걸리는지 |
| `rules.mjs` | 마크다운 표 파싱, 깨진 행을 조용히 버리는지 |
| `lint.mjs` | 규칙마다 양성 사례와 음성 사례 한 쌍씩 |
| `applyFixes` | 받침 판정, 조사 안전장치, 뒤에서부터 고쳐 위치가 어긋나지 않는지 |
| `build-style.mjs` | 순위 컷, 출력 길이 상한, 커밋된 생성물이 최신인지 |
| `guard-artifact.mjs` | heredoc 커밋 메시지 추출, 문서 확장자 필터, 세 환경변수, 망가진 입력 |

`build-style.mjs`의 최신 여부 확인이 중요하다. `rules/`를 고치고 스타일 파일을 다시 생성하지 않으면
자료와 제품이 어긋난다. `npm test`가 `--check`를 먼저 돌려 그것을 막는다.

### 2. 규칙표 정합성 (`tests/corpus.test.mjs`)

규칙이 수백 개로 자라면 사람 눈으로 못 잡는 실패가 생긴다. 코드로 막는다.

| 시험 | 잡으려는 실패 |
|---|---|
| 쓸 것이 다른 규칙에 걸리지 않는다 | A가 권하는 표현이 B의 금칙어인 순환 |
| 치환 규칙은 자기 자신을 다시 잡지 않는다 | 고친 결과를 무한히 다시 지적하는 것 |
| 쓰지 말 것이 중복되지 않는다 | 같은 금칙어에 다른 대체 표현이 붙는 것 |
| 깨끗한 한국어 문장에 아무 규칙도 걸리지 않는다 | 규칙이 너무 공격적이어서 생기는 오탐 |
| 치환 규칙은 실제로 치환할 수 있다 | 치환으로 표시했는데 동작하지 않는 것 |
| 한 글자 금칙어에 문자열 검사를 걸지 않는다 | 오탐 폭발 |

네 번째 시험이 규칙 추가의 브레이크 역할을 한다. 깨끗한 예시 문장 여덟 개 중 하나라도 걸리기
시작하면 새로 넣은 규칙이 너무 공격적이라는 신호다.

### 3. 출력 스타일 적재 확인 (`tests/style-file.test.mjs`)

가장 나쁜 실패를 막는 시험이다. 프런트매터에 모르는 키가 있으면 클로드 코드가
`Skipping plugin output-style` 하고 조용히 건너뛴다. 그러면 플러그인은 설치돼 있는데 아무 일도
하지 않고 아무도 알아채지 못한다.

허용되는 키는 네 개뿐이다: `name`, `description`, `keep-coding-instructions`, `force-for-plugin`.
시험이 그 밖의 키를 거부하고, `keep-coding-instructions: true`와 `force-for-plugin: true`가
켜져 있는지, 그리고 편향을 거스르는 문장들이 본문에 남아 있는지 확인한다.

### 4. 골든 파일

`output-styles/natural-korean.md`를 커밋한다. 규칙 한 줄을 고치면 생성물 diff가 리뷰에 드러난다.
이 플러그인은 프롬프트가 제품이므로 프롬프트 변경이 코드 변경처럼 검토되어야 한다.

### 5. 말투와 품질 평가 (`evals/`)

`claude plugin eval .`로 돌린다. `--ablation`이 기본으로 `with-without`이라 플러그인을 켠 팔과
끈 팔을 모두 돌려 점수 차이를 보고한다. 우리가 보고 싶은 것이 정확히 그 차이다.

| 사례 | 겨냥하는 것 | 기대 |
|---|---|---|
| `tone-paraphrase` | 풀어쓰기 편향. 영향 범위/멱등/경쟁 조건/결합도를 쓰는지 | 켬 > 기준선 |
| `tone-metaphor` | 은유 직역. "얇은 계약" 류 | 켬 > 기준선 |
| `tone-pangyo` | 한영 혼용 | 켬 > 기준선 |
| `tone-translationese` | 번역체 문장 구조 | 켬 > 기준선 |
| `tone-notation` | 외래어 표기 | 켬 > 기준선 |
| `english-passthrough` | 영어로 물으면 영어로 답하는지 | 켬 = 기준선 |
| `quality-preserved` | `forEach` + `async` 버그를 정확히 짚는지 | 켬 = 기준선 |

마지막 두 사례가 첫 다섯 개만큼 중요하다. **말투가 좋아지고 실력이 떨어지면 실패다.**
`quality-preserved`의 점수가 기준선보다 낮으면 스타일 본문이 작업을 방해하고 있다는 뜻이고,
그때는 `MAX_CHARS`를 줄이거나 `순위`를 다시 매겨 본문을 줄여야 한다.

채점기는 `regex`를 먼저 쓴다. 무료이고 판정이 흔들리지 않는다. 목록으로 잡을 수 없는 것(문장 구조,
기술적 정확성)만 `llm` 채점기에 맡긴다.

### 6. 손으로 채점하기 (`scripts/score-response.mjs`)

자격 증명 없이 말투를 재는 도구다. 답변을 표준 입력으로 넣으면 위반 목록과 한글 1000자당 밀도를
알려 준다. `--fix`를 주면 치환 규칙을 적용한 결과를 내보낸다.

```bash
cat 답변.md | node scripts/score-response.mjs
node scripts/score-response.mjs --json 답변.md   # CI 채점용
```

## 출시 순서

- **v0.1** — 출력 스타일 + `rules/` + `build-style.mjs` + 단위 테스트. 훅 없음.
- **v0.2** — `guard-artifact` 린터.
- **v0.3** — 평가 세트.

v0.1이 제품의 대부분이다. 린터는 커밋과 문서에만 걸리고 대화 말투는 건드리지 못한다. 먼저 스타일만
내놓고 실제로 좋아지는지 확인한 다음 린터를 붙이는 것이 순서상 맞다.

## 알려진 한계

1. **대화 텍스트는 사후 검사만 가능하다.** 어시스턴트가 말하기 직전에 끼어드는 훅이 없다. Stop 훅으로
   검사하면 사용자는 "어색한 한국어 → 고친 한국어"를 연달아 보게 된다. 그래서 대화 텍스트에 대해서는
   예방(출력 스타일)만 하고 사후 교정은 하지 않는다.
2. **린터는 목록에 있는 것만 잡는다.** 번역체 문장 구조처럼 목록화되지 않는 문제는 출력 스타일에 의존한다.
3. **강제 적용은 다른 출력 스타일을 배제한다.** 위의 "강제 적용의 대가" 참조.
4. **규칙 자료의 품질이 제품의 품질이다.** 배선은 작고 자료가 크다. 잘못된 항목은 도움이 아니라 해가 된다.
5. **평가는 자격 증명이 있는 환경에서만 돌아간다.** `claude plugin eval`은 자식 `claude` 프로세스를
   띄우는데, 그 프로세스가 자격 증명을 물려받지 못하면 모든 사례가 인증 오류로 실패한다. AWS Bedrock
   경유 세션 안에서 특히 그렇다. 사례 파일 자체는 적재되고 `regex` 채점기도 도는 것을 확인했지만,
   실행은 사람이 직접 셸에서 해야 한다. 자격 증명이 필요 없는 검증은 `npm test`에 들어 있다.

## 설계 중 뒤집은 결정

같은 실수를 반복하지 않기 위해 기록해 둔다.

### 스킬 → 출력 스타일

처음에는 큰 용어집을 스킬에 두고 모델이 필요할 때 열어 보게 하려 했다. 잘못된 설계다. 말투는 매 문장에
적용되어야 하는 규칙이므로 모델의 판단에 맡길 수 없다. 스킬과 슬래시 커맨드를 모두 없앴다.

### "자연스러운 우리말로 풀어쓰기" → "한자어 기술용어 우선"

처음 정한 용어 원칙의 2순위가 "자연스러운 우리말로 풀고 첫 등장에 원어 병기"였다. 이 원칙이 잘못된
결과를 만들어 냈다. 실제로 설계 중에 같은 방향으로 두 번 연속 틀렸다.

| 원문 | 첫 시도 | 두 번째 시도 | 맞는 표현 |
|---|---|---|---|
| thin contract | 얇은 계약 | 모듈끼리 서로 알아야 하는 것을 최소로 줄이세요 | 결합도를 낮추세요 |
| blast radius | — | 여파가 미치는 범위 | 영향 범위 |

두 번째 시도들은 전부 순우리말로 풀어쓴 서술문이다. 문법은 맞지만 어색하다. 한국어 기술 레지스터의
실제 어휘는 한자어 술어이고, 그것이 더 짧고 정확하고 이미 통용된다.

이것은 모델의 체계적 편향으로 보인다. "자연스러운 한국어"라는 지시를 받으면 순우리말 풀어쓰기로 기울고
그 결과가 번역 투로 읽힌다. 따라서 출력 스타일은 이 편향을 **명시적으로 거슬러야** 한다. 풀어쓰기를
최후 수단으로 못박은 4번 규칙이 그 장치다.

### 은유 층의 발견

실패 유형이 두 층이 아니라 세 층이었다.

1. **단어 층** — `레더` 같은 음차. 잡기 쉽다.
2. **문장 구조 층** — `우리는 ~한다` 같은 번역체. 정규식으로 일부 잡힌다.
3. **은유 층** — `얇은 계약`. 단어도 한국어고 문법도 맞는데 비유가 영어라서 통하지 않는다.

3번이 가장 잡기 어렵다. 앞의 두 층을 모두 통과하기 때문이다. 게다가 은유마다 정착 여부가 다르다.
`무거운 작업`, `가벼운 라이브러리`, `코드 냄새`, `일급 함수`는 한국어에 뿌리내렸고 `얇다`, `두껍다`,
`깊다`, `평평하다`는 내리지 않았다. 원칙으로 이 구분을 유도할 수 없으므로 `rules/metaphors.md`에
사례를 판정해 둔다.

### 차단 → 경고

린터의 기본 동작을 차단으로 설계했다가 경고로 내렸다. "클로드의 퀄리티는 유지"라는 제약이 들어오면서
판단이 바뀌었다. 커밋을 문체 때문에 막으면 작업 흐름이 끊기고 재시도 턴을 낭비하며 최악의 경우 원래
하려던 일을 잊는다.

### 검사 두 값 → 세 값

`검사` 열을 `정규식`과 `프롬프트` 두 값으로 설계했다. 그런데 훅 출력 명세에서 `updatedInput`을
발견했다. PreToolUse 훅이 도구 입력을 직접 고쳐 쓸 수 있다는 뜻이고, 그러면 린터가 경고만 하는 것이
아니라 결정론적으로 교정할 수 있다.

능력이 셋이 되었으므로 값도 셋이 되어야 했다. `치환`(자동 교정 가능), `정규식`(경고만),
`프롬프트`(스타일만). 세 값이 세 능력에 정확히 대응한다.

그런데 치환에는 한국어 고유의 함정이 있었다. 조사다. 위의 "자동 교정의 조사 문제" 참조.
이 함정 때문에 `치환` 여부를 사람이 손으로 정하면 안 된다는 결론이 나왔고, `import-corpus.mjs`가
실제 치환을 해 보고 계산하도록 만들었다.

### 규칙 자료를 손으로 쓰려던 계획 → 조사로 모으고 검증하기

설계 중에 같은 방향으로 두 번 연속 틀린 뒤, 규칙 자료를 손으로 쓰는 것을 포기했다. 대신 분류별로
초안을 만들고, 각 초안을 반대편에서 검증하고, 전체를 교차 감사하는 과정을 거쳤다. 검증 단계의
최우선 항목은 "쓸 것이 풀어쓰기로 늘어져 어색하지 않은가"였다. 실제로 분류마다 다섯에서 여섯 건이
그 이유로 교정되었다.

인스턴스가 4대라면 **어떤 데이터를 캐시할지**에 따라 결론이 달라집니다. 주문 상태처럼 자주 바뀌는 데이터라면 Redis가 안전하고, 상품 정보나 쿠폰 규칙처럼 잘 바뀌지 않는 참조 데이터라면 프로세스 안 LRU 캐시로도 충분합니다.

## 비교

| 항목 | 프로세스 안 LRU | Redis |
|---|---|---|
| 응답 속도 | 메모리에 바로 접근하므로 수백 ns 수준입니다 | 네트워크 왕복이 필요해서 보통 0.2~1ms 정도 걸립니다 |
| 인스턴스 사이 일관성 | 인스턴스마다 캐시를 따로 가지므로, 한 대에서 값을 갱신해도 나머지 3대에는 이전 값이 남습니다 | 모든 인스턴스가 캐시 하나를 공유하므로 무효화가 한 번에 끝납니다 |
| 적중률 | 같은 키를 4대가 각각 채워야 하므로 적중률이 낮아지고, DB 부하도 최대 4배까지 늘어납니다 | 한 번 채운 값을 모든 인스턴스가 함께 사용합니다 |
| 메모리 | 같은 데이터가 4벌 복제되고, 애플리케이션 힙을 차지하므로 GC에도 부담을 줍니다 | 캐시 용량을 애플리케이션과 분리해서 관리할 수 있습니다 |
| 배포와 재시작 | 재시작하면 캐시가 비워지므로, 롤링 배포 직후에 DB 요청이 일시적으로 몰립니다 | 배포해도 캐시가 유지됩니다 |
| 운영 부담 | 추가 인프라가 필요하지 않습니다 | Redis를 운영하고 모니터링해야 하며, Redis 장애가 서비스 장애로 번지지 않도록 대비해야 합니다 |
| 부가 기능 | 캐시 기능만 제공합니다 | 분산 락, 멱등성 키, 레이트 리밋처럼 주문 서비스에 유용한 기능도 함께 구현할 수 있습니다 |

## 주문 서비스에서 특히 주의할 점

- **주문 상태와 재고, 결제 정보는 이전 값을 읽으면 곤란합니다.** 로컬 LRU를 사용하면 A 인스턴스에서 주문을 취소했는데 B 인스턴스는 여전히 "결제 완료"로 응답하는 상황이 생길 수 있습니다. 이런 데이터를 로컬에 캐시하려면 Redis Pub/Sub이나 메시지 큐로 무효화 이벤트를 전파해야 하는데, 결국 그 방식도 외부 인프라가 필요합니다.
- **짧은 TTL로 불일치를 감수할 수 있는 데이터라면** 로컬 LRU가 가장 간단하고 빠릅니다. 예를 들어 상품 가격표나 쿠폰 정책을 TTL 30초로 캐시해도 문제가 없다면, Redis를 새로 도입할 이유가 크지 않습니다.

## 권장 방향

1. 캐시하려는 데이터가 **읽기 위주이고 수 초~수십 초 정도의 불일치를 허용한다면**, 로컬 LRU에 짧은 TTL을 설정하는 방식부터 시작하는 것을 권장합니다.
2. **쓰기가 잦거나 인스턴스 사이에서 즉시 일관성이 필요하다면** Redis를 사용합니다.
3. 두 종류가 섞여 있다면, 로컬 LRU를 L1으로 두고 Redis를 L2로 두는 2단 구성도 가능합니다. 다만 무효화 경로가 두 겹이 되므로 복잡도가 올라간다는 점을 감안해야 합니다.

어떤 데이터를 캐시할 계획인지, 그리고 이미 Redis를 운영하고 있는지 알려주시면 더 구체적으로 추천해 드리겠습니다. 이번 답변은 일반적인 기준으로 비교한 것이고, 저장소 코드는 확인하지 않았습니다.

인스턴스가 4대이고 캐시할 대상이 주문 데이터라면 **Redis 쪽을 권합니다.** 주문은 상태가 계속 바뀌는 데이터라서, 무효화를 4대에 맞춰 주는 일이 가장 어렵습니다. 프로세스 안 LRU 캐시는 이 부분이 약합니다.

## 비교

| 항목 | 프로세스 안 LRU | Redis |
|---|---|---|
| 지연 시간 | 메모리 접근이라 수 µs 수준 | 네트워크를 한 번 거쳐 보통 0.2~1ms, 직렬화 비용도 추가 |
| 인스턴스 간 일관성 | 4대가 각자 캐시를 가짐. A에서 주문을 수정해도 B~D에는 오래된 값이 남음 | 캐시가 하나라 수정 후 한 번만 무효화하면 됨 |
| 적중률 | 캐시를 4대가 따로 채우므로 같은 키도 4번 미스가 남. 로드밸런서가 요청을 고르게 나누면 적중률이 떨어짐 | 한 인스턴스가 채우면 나머지도 적중 |
| 메모리 | 같은 데이터가 4벌 저장되고 애플리케이션 힙을 차지함. GC 부담도 커짐 | 별도 서버에 한 벌만 저장 |
| 배포·재시작 | 재시작하면 캐시가 비어서 배포 직후 DB 부하가 몰림 | 배포와 상관없이 캐시가 유지됨 |
| 운영 부담 | 라이브러리 하나로 끝나고 인프라 추가가 없음 | Redis 운영, 모니터링, 장애 대응이 필요함. 가용성을 챙기려면 Sentinel이나 관리형 서비스까지 고려해야 함 |
| 장애 영향 범위 | 캐시가 해당 프로세스 안에만 있어서 영향이 그 인스턴스로 끝남 | Redis가 죽으면 4대가 동시에 DB로 몰릴 수 있음. 폴백과 타임아웃 설정이 필수 |
| 부가 기능 | 없음 | 분산 락, 카운터, pub/sub, TTL 등을 같이 쓸 수 있음 |

## 주문 서비스에서 따져 볼 점

- **주문 상태가 자주 바뀝니다.** 결제 완료, 배송 중, 취소처럼 상태가 바뀔 때 사용자가 이전 상태를 보면 바로 문의나 버그 리포트로 이어집니다. LRU를 쓰면 TTL을 아주 짧게 잡거나, 수정이 일어날 때 pub/sub로 4대에 무효화 메시지를 뿌려야 합니다. 이렇게까지 구현하면 사실상 Redis를 도입하는 셈입니다.
- **어떤 데이터를 캐시할지에 따라 답이 달라집니다.** 상품 카탈로그, 배송비 정책, 쿠폰 규칙처럼 거의 바뀌지 않고 조금 늦게 반영돼도 괜찮은 데이터라면 LRU에 TTL 몇십 초만 줘도 충분합니다. 이런 데이터에는 Redis가 과합니다.
- **캐시를 넣으려는 이유도 따져 봐야 합니다.** DB 부하를 줄이는 게 목적이면 인스턴스끼리 캐시를 공유하는 Redis가 유리합니다. 핫 패스의 지연 시간을 µs 단위로 줄이는 게 목적이면 LRU가 유리합니다.

## 둘 다 필요할 때

읽기가 많은 조회 API라면 2단 구성도 자주 씁니다.

- L1: 프로세스 안 LRU, TTL 1~5초
- L2: Redis, 필요한 만큼 긴 TTL
- 수정이 일어나면 Redis에서 키를 지우고, pub/sub로 각 인스턴스의 L1도 무효화

다만 처음부터 이렇게 가면 복잡도가 꽤 올라갑니다. Redis만으로 시작하고, 측정해 보니 Redis 왕복 시간이 병목일 때 L1을 붙이는 순서를 추천합니다.

어떤 데이터를 캐시하려는지 알려 주시면 TTL과 무효화 시점까지 구체적으로 잡아 드리겠습니다. 예를 들어 주문 상세, 주문 목록, 장바구니 합계 중 무엇인지 알려 주시면 됩니다.

인스턴스가 4대라는 점이 판단에 가장 크게 영향을 줍니다. 두 방식을 비교하면 이렇습니다.

## 프로세스 안 LRU 캐시

**장점**
- 지연 시간이 가장 짧습니다. 네트워크를 거치지 않으니 조회가 마이크로초 단위로 끝납니다.
- 인프라를 추가하지 않아도 됩니다. 운영, 모니터링, 장애 대응할 대상이 늘지 않습니다.
- 캐시가 죽어서 서비스가 같이 죽는 일이 없습니다.

**단점**
- **인스턴스 4대가 캐시를 따로 가집니다.** 주문 상태가 바뀌어 A 인스턴스에서 캐시를 무효화해도 B, C, D에는 이전 값이 남습니다. 로드밸런서가 요청을 여기저기 보내면 같은 사용자가 새로고침할 때마다 다른 상태를 보게 됩니다.
- 이걸 막으려면 Redis Pub/Sub이나 메시지 큐로 무효화 이벤트를 뿌려야 하는데, 그러면 결국 외부 인프라가 필요해집니다.
- 적중률이 떨어집니다. 같은 키를 인스턴스마다 한 번씩 원본에서 읽어 와야 하니 DB 부하가 최대 4배로 늘어납니다.
- 배포나 재시작을 하면 캐시가 비어서 직후에 DB 부하가 몰립니다.
- 힙 메모리를 나눠 쓰므로 캐시 크기가 곧 GC 부담이 됩니다.

## Redis

**장점**
- 4대가 같은 캐시를 보니 일관성 문제가 훨씬 단순해집니다. 한 곳에서 지우면 모든 인스턴스에 반영됩니다.
- 적중률이 높고, 인스턴스를 늘려도 DB 부하가 같이 늘지 않습니다.
- 재배포해도 캐시가 유지됩니다.
- TTL, 분산 락, 원자적 연산(`INCR`, `SETNX`)을 쓸 수 있어서 재고 차감이나 중복 주문 방지 같은 용도로도 확장할 수 있습니다.

**단점**
- 조회마다 네트워크 왕복이 생깁니다. 같은 VPC 안이면 보통 1ms 안팎이지만 LRU보다는 확실히 느립니다.
- 운영 대상이 하나 늘어납니다. 메모리 한도, 퇴출 정책, 복제와 장애 조치를 설정해야 합니다.
- Redis 장애 시 동작을 정해 둬야 합니다. 캐시를 건너뛰고 DB로 바로 가게 할지, 서킷 브레이커를 둘지 결정해야 하고, 한꺼번에 DB로 몰리는 상황도 대비해야 합니다.
- 직렬화 비용이 있고, 비용도 추가로 듭니다.

## 추천

**주문 서비스라면 Redis를 권합니다.** 주문 데이터는 상태가 자주 바뀌고(결제 대기 → 결제 완료 → 배송 중), 사용자가 오래된 상태를 보면 바로 문의나 중복 결제로 이어집니다. 인스턴스 4대에서 LRU를 쓰면 이 일관성 문제를 직접 풀어야 하는데, 그 비용이 Redis 운영 비용보다 큽니다.

다만 데이터 성격에 따라 나눠 쓰는 것도 괜찮습니다.

| 데이터 | 권장 | 이유 |
|---|---|---|
| 주문 상태, 주문 상세 | Redis | 자주 바뀌고 일관성이 중요합니다 |
| 상품 카테고리, 배송 정책, 코드 테이블 | 로컬 LRU (짧은 TTL) | 거의 안 바뀌고, 몇십 초 늦게 반영돼도 문제가 없습니다 |
| 쿠폰 사용 여부, 재고 | 캐시보다 DB나 Redis 원자 연산 | 캐시에서 오래된 값을 읽으면 중복 사용이나 초과 판매가 생깁니다 |

조회량이 아주 많아서 Redis 왕복마저 병목이 되면, 그때 로컬 LRU를 앞에 두고 Redis를 뒤에 두는 2단 구성을 검토하시면 됩니다. 처음부터 2단으로 가면 무효화 경로가 두 개가 되어 복잡해지니, Redis 하나로 시작하시는 편을 권합니다.

캐시를 붙이려는 조회가 어떤 건지(주문 상세인지, 주문 목록인지, 쿠폰 계산 쪽인지) 알려 주시면 키 설계와 무효화 시점까지 구체적으로 정리해 드리겠습니다.

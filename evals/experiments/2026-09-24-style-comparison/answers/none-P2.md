## 리뷰 코멘트의 뜻

"캐시 계층이 가격 계산 로직에 너무 강하게 묶여 있다"는 뜻입니다. `src/cart.mjs`에서 **캐싱**(결과를 저장했다가 다시 쓰는 일)과 **가격 계산**(합계와 쿠폰 할인)이 한 함수 `total()` 안에 섞여 있다는 지적입니다.

```js
const cache = new Map();                      // 캐시가 모듈 전역에 박혀 있음

export function total(items, coupon) {
  const key = JSON.stringify(items);          // 캐시 키를 가격 함수가 직접 만듦
  if (cache.has(key)) return cache.get(key);
  let sum = 0;
  for (const item of items) sum += item.price * item.qty;
  if (coupon) sum = sum - sum * coupon.rate;  // 가격 규칙
  cache.set(key, sum);
  return sum;
}
```

이렇게 섞여 있으면 생기는 문제는 다음과 같습니다.

1. **가격 규칙을 바꿀 때마다 캐시 키도 같이 고쳐야 합니다.** 쿠폰 기능이 들어오면서 결과가 `coupon`에도 달라지게 됐는데, 키는 여전히 `items`만으로 만들고 있습니다. 이 때문에 실제로 버그가 생겼습니다. `npm test`를 돌려보면 "10% 쿠폰" 테스트가 `expected: 22500, actual: 25000`으로 실패합니다. 같은 `items`로 쿠폰 없이 먼저 계산한 값이 캐시에 남아 있다가 그대로 반환되기 때문입니다. 강한 결합이 실제로 어떤 피해를 주는지 보여주는 사례입니다.
2. **캐시 없이 테스트하거나 쓸 수 없습니다.** 모듈 전역 `Map`이라 테스트끼리 상태가 섞이고, 캐시를 끄거나 초기화할 방법이 없습니다.
3. **캐시 정책을 바꾸기 어렵습니다.** 크기 제한(LRU), TTL, 외부 캐시 등으로 바꾸려면 가격 함수를 직접 고쳐야 합니다.
4. 부수 효과로, 캐시에 제한이 없어서 메모리가 계속 늘어납니다.

## 고치는 방향

핵심은 **순수한 계산 함수와 캐싱을 분리하는 것**입니다.

**1단계: 가격 계산을 순수 함수로 만들기**
`calculateTotal(items, coupon)`은 합계와 할인만 계산하고, 캐시는 전혀 모르게 합니다. 입력이 같으면 항상 같은 결과가 나오므로 테스트하기 쉽습니다.

**2단계: 캐싱을 범용 래퍼로 따로 두기**
`memoize(fn, keyFn)` 같은 함수가 "함수를 받아 결과를 캐싱하는 함수"를 돌려주게 합니다. 키를 만드는 방식은 이 함수를 쓰는 쪽에서 넘겨줍니다. 예를 들어 `(items, coupon) => JSON.stringify([items, coupon])`처럼 **모든 인자**를 키에 넣습니다.

**3단계: 두 부분을 조립해서 export하기**
`export const total = memoize(calculateTotal, keyFn)`처럼 합칩니다. 외부 API인 `total(items, coupon)`은 그대로라서 호출하는 쪽은 바뀌지 않습니다. 필요하면 캐시 인스턴스를 주입받게 해서, 테스트에서는 캐시 없이 쓰거나 새 캐시를 넣을 수 있게 합니다.

이렇게 나누면 나중에 가격 규칙이 늘어나도(배송비, 회원 등급 등) 계산 함수만 고치면 되고, 캐시 쪽은 키 함수만 맞추면 됩니다. 두 관심사가 서로의 내부를 알 필요가 없어집니다.

추가로 캐시가 정말 필요한지도 검토해볼 만합니다. 장바구니 합계는 계산이 매우 가벼워서, `JSON.stringify`로 키를 만드는 비용이 계산 자체보다 클 수 있습니다. 캐시를 아예 없애는 것도 간단하고 좋은 해결책입니다.

요청하신 대로 코드는 수정하지 않았습니다.

인스턴스가 4대라면 **데이터 성격에 따라 결정이 갈립니다.** 주문 서비스는 대부분 정합성이 중요한 데이터를 다루기 때문에, 기본은 Redis로 두고 일부 읽기 전용 데이터에만 로컬 LRU를 쓰는 방식을 추천합니다.

## 비교

| 항목 | 프로세스 내 LRU | Redis |
|---|---|---|
| **지연 시간** | 약 100ns 수준으로 매우 빠름 | 네트워크를 거쳐 0.2~1ms |
| **인스턴스 간 일관성** | ❌ 4대가 각자 캐시를 가져서 무효화가 어려움 | ✅ 하나의 저장소를 공유 |
| **히트율** | 캐시가 4개로 나뉘어 낮아짐. 같은 키가 4번 미스날 수 있음 | 전체가 하나의 캐시라 높음 |
| **메모리** | 같은 데이터가 4번 중복 저장되고 앱 힙을 차지함 (GC 부담) | 별도 메모리를 쓰고 따로 확장 가능 |
| **배포·재시작** | 재시작하면 비워진 상태로 시작해서 배포 직후 DB 부하가 몰림 | 캐시가 유지됨 |
| **운영 부담** | 없음 | Redis 운영, 장애 대응, 모니터링, 비용이 필요 |
| **장애 지점** | 없음 | Redis가 죽으면 DB로 넘어가는 경로(fallback)와 타임아웃 처리가 필요 |
| **부가 기능** | 없음 | TTL, 분산 락, 멱등키, 레이트 리밋, pub/sub |

## 주문 서비스에서 판단 기준

**Redis가 맞는 경우**
- 주문 상태, 재고, 쿠폰 사용 여부처럼 **바뀌고 틀리면 안 되는 데이터**. 로컬 캐시에서는 인스턴스 A가 갱신해도 B~D에는 오래된 값이 남습니다.
- 장바구니나 세션처럼 **요청이 어느 인스턴스로 가도 같은 값을 봐야 하는 데이터**
- 중복 주문을 막는 멱등키나 쿠폰 중복 사용을 막는 락. 로컬 캐시로는 아예 구현할 수 없습니다.

**로컬 LRU가 맞는 경우**
- 상품 기본 정보, 카테고리, 설정값, 할인 정책 정의처럼 **읽기가 많고 거의 안 바뀌며, 몇 초~몇 분 늦게 반영돼도 괜찮은 데이터**
- 짧은 TTL(예: 30~60초)을 두면 무효화 문제를 대부분 피할 수 있습니다.
- 초당 수천 번 이상 조회되는 **핫 키**라 Redis 왕복 시간조차 부담될 때

## 추천 구성

1. **1단계는 Redis 하나로 시작하세요.** 4대 규모에서는 일관성과 단순함의 이점이 지연 시간 차이보다 큽니다.
   - cache-aside 패턴을 쓰고, 쓰기 시 키를 삭제합니다.
   - TTL에 약간의 무작위 값(jitter)을 더해 만료가 한꺼번에 몰리지 않게 합니다.
   - Redis 타임아웃은 50~100ms 정도로 짧게 잡고, 실패하면 DB로 넘어가게 합니다.
2. **2단계로, 측정해서 핫 키가 보이면** 그 데이터에만 로컬 LRU를 앞단에 둡니다(L1 로컬 + L2 Redis 2단 구성).
   - 무효화는 짧은 TTL로 하거나, Redis pub/sub으로 4대에 삭제 이벤트를 방송합니다.
3. **주문 확정, 결제, 재고 차감 경로는 캐시를 거치지 말고** 항상 DB 기준으로 처리하세요.

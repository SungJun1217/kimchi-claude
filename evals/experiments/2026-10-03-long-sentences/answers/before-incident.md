# 주문 API 지연 장애 회고

14:00 배포 직후 주문 API의 p95가 180ms에서 2.4s로 올랐습니다. 14:12에 롤백했고 14:15에 p95가 정상 수준으로 돌아왔습니다. 확인된 사실과 아직 추정인 부분을 나누어 적고, 캐시 도입 조건과 재발 방지 방안을 정리합니다.

먼저 확인된 사실입니다. 새 코드는 매 요청마다 사용자 권한을 DB에서 조회했습니다. p95는 배포 시점에 맞춰 올랐고 롤백 3분 뒤 원래대로 돌아왔으므로, 이번 배포가 지연의 원인이라는 점은 확정으로 봅니다. 장애 중 DB 연결 대기 시간은 늘었지만 DB CPU는 평소 수준이었습니다.

여기서부터는 추정입니다. 연결 대기만 늘고 CPU가 그대로라면, 쿼리 하나가 무거웠다기보다 요청마다 추가된 조회가 커넥션 풀을 오래 점유해서 요청들이 연결을 기다렸을 가능성이 큽니다. 다만 커넥션 풀 사용률이나 쿼리별 소요 시간으로 직접 확인하지는 못했습니다. 그래서 권한 조회 쿼리 자체가 느렸는지, 호출 수가 많아서 풀이 모자랐는지는 아직 구분하지 못했습니다. 오류율과 영향받은 사용자 수도 지금 가진 자료로는 확인되지 않아 이 문서에 쓰지 않았습니다. 이 부분은 메트릭을 다시 확인해 채워야 합니다.

권한 캐시는 조회 부하를 줄이는 가장 직접적인 방법입니다. 하지만 권한을 회수한 직후에도 캐시에 남은 오래된 권한으로 접근이 허용될 수 있어서, 속도만 보고 넣을 수는 없습니다. 아래 조건을 만족할 때 도입하자고 제안합니다. 우선 권한 회수 후 접근이 허용되어도 되는 최대 시간을 보안 담당과 함께 정하고, TTL은 그 값 이하로 잡습니다. 권한을 회수하는 시점에는 해당 사용자의 캐시를 즉시 무효화하고, TTL은 무효화가 실패했을 때를 위한 마지막 안전장치로만 둡니다. 결제나 관리자 기능처럼 오래된 권한이 허용되면 피해가 큰 동작은 캐시를 거치지 않고 DB에서 직접 확인합니다. 도입 후에는 캐시 적중률, 무효화 지연, 캐시와 DB의 권한 불일치 건수를 측정해 이 조건이 실제로 지켜지는지 봅니다.

캐시 결정과 별개로 재발 방지책도 필요합니다. 요청당 DB 호출이 늘어나는 변경은 배포 전에 부하 테스트로 p95와 커넥션 풀 사용률을 확인하는 절차를 넣겠습니다. 배포는 일부 트래픽부터 시작하는 카나리로 진행하고, p95와 DB 연결 대기 시간에 알림을 걸어 기준을 넘으면 자동으로 롤백되게 하겠습니다. 캐시 없이도 권한 조회를 요청 안의 다른 조회와 묶어 호출 횟수를 줄일 수 있는지도 먼저 검토합니다.

마지막으로 배포부터 롤백까지 12분이 걸린 이유는 이번 자료만으로는 알 수 없습니다. 알림이 늦었는지, 원인 판단에 시간이 걸렸는지 타임라인을 따로 복기해서 감지와 판단 단계의 개선점을 찾겠습니다.

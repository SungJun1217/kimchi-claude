# 한국의 식별번호와 개인정보

## 먼저 알아야 할 것 두 가지

**주민등록번호는 검증할 수 없습니다.** 2020년 10월부터 뒷자리 중 지역 표시와 검증 번호가
없어지고 임의로 발급됩니다. 오래 알려진 체크섬 알고리즘은 그 이후 발급된 번호에 통하지
않으므로, 검증하는 코드는 **정상 번호를 거부합니다.** 한국 코드베이스에 아직 많이 남아
있는 버그이고 새로 짤 때 가장 하기 쉬운 실수입니다.

**그리고 애초에 저장하지 않는 것이 맞습니다.** 개인정보 보호법은 법령에 구체적 근거가 있는
경우로 주민등록번호 처리를 제한합니다. 근거 없이 수집하면 위법입니다. "혹시 필요할까 봐"
받아 두는 설계를 제안하지 마십시오.

## 주민등록번호 대신 무엇을 쓰나

| 하려는 일 | 쓸 것 |
|---|---|
| 본인 확인 | 본인인증 기관의 CI(연계정보). 번호 자체를 보관하지 않습니다 |
| 중복 가입 차단 | CI 로 판단합니다. 서비스가 달라도 같은 사람은 같은 CI 입니다 |
| 서비스 내 식별 | DI(중복가입확인정보). 서비스별로 다른 값입니다 |
| 나이·성인 확인 | 생년월일이나 성인 여부만 받습니다 |
| 실명 확인 | 본인인증 **결과**만 보관합니다 |

법령 근거가 있어 정말로 보관해야 하면 암호화가 의무이고, 화면·로그·오류 보고에는 마스킹한
값만 나가야 합니다.

## 검증할 수 있는 번호들

사업자등록번호(10자리)와 법인등록번호(13자리)는 체크섬이 살아 있어 검증할 수 있습니다.
**두 번호의 알고리즘이 다릅니다.** 가중치도 계산 방식도 달라서 한 함수로 처리하면 틀립니다.

동작하는 구현: `examples/business-number.mjs`

```js
import { isValidBusinessNumber, isValidCorporateNumber } from "./examples/business-number.mjs";

isValidBusinessNumber("123-45-67891"); // true, 하이픈이 있어도 된다
isValidCorporateNumber("1234567890120"); // 가중치가 1·2 번갈이로 다르다
```

## 마스킹

되돌릴 수 없어야 합니다. 앞뒤를 조금씩 남기면 다른 정보와 합쳐 복원됩니다. 특히 생년월일과
이름을 함께 남기면 사실상 식별됩니다.

| 대상 | 남기는 것 | 주의 |
|---|---|---|
| 이름 | 첫 글자와 끝 글자 | 성이 두 글자인 경우(남궁, 황보)를 자동으로 알 수 없어 성을 분리하지 않습니다 |
| 주민등록번호 | 생년월일만 | 성별 자리도 가립니다. 생년월일과 성별이 함께 남으면 식별될 수 있습니다 |
| 전화번호 | 앞자리와 뒤 네 자리 | 서울은 지역번호가 두 자리입니다 |
| 전자우편 | 계정 앞 두 글자와 도메인 | 도메인은 남겨야 문제를 진단할 수 있습니다 |
| 계좌·카드 | 뒤 네 자리만 | 카드 앞 여섯 자리(BIN)도 남기지 않습니다. 카드사와 상품이 드러납니다 |
| 주소 | 도로명과 건물번호 | 동·호수를 남기면 특정됩니다 |

동작하는 구현: `examples/masking.mjs`

## 로그와 오류 보고에 새는 것

주민등록번호가 코드에 들어가는 경로는 대개 다음 셋입니다.

1. 시험 자료에 실제 번호를 씀 — 형식만 맞는 가짜 번호를 쓰십시오
2. 요청 본문을 그대로 로그에 남김 — 필드 단위로 골라 남기십시오
3. 오류 추적 도구에 요청 전체를 보냄 — 전송 전에 마스킹 훅을 두십시오

`examples/resident-number.mjs` 의 `findResidentNumbers()` 로 글에 섞인 것을 찾을 수 있습니다.
커밋 전 검사나 로그 전송 훅에 걸어 쓰십시오.

## 자주 틀리는 것

- 주민등록번호를 체크섬으로 검증하기 — 2020년 10월 이후 번호를 거부합니다
- 주민등록번호를 기본키나 회원 식별자로 쓰기 — 법적 근거가 없고 바꿀 수도 없습니다
- 성별 자리를 1·2 만 다루기 — 외국인은 5~8 입니다
- 출생 연도를 두 자리로 저장하기 — 성별 자리가 세기를 결정합니다
- 사업자등록번호를 법인등록번호와 같은 함수로 검증하기
